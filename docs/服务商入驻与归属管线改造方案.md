## 1. 设计目标与总原则

1. **单一入驻真源**：所有"成为 SERVICE_PROVIDER"必须走 `QualificationApplication` 的两段审（agent 一审 + ADMIN 终审），`role` **仅在 `APPROVED` 落地**。删/收口自服务捷径。
2. **区域化辖区归属**：服务商注册时绑定 `regionPath`；终审通过时按最长前缀匹配写入 `User.agentId`，消除"隐式软匹配 + 空字段"隐患；代理商 `regionPath` 唯一。
3. **分段闸门、责任清晰**：agent = 辖区一审监督（资质/提现/内容红线），**不做身份变更、不放资金、不终审、不发布**；ADMIN = 终审裁定 + 资金闸门。
4. **合同硬闸门**：总台 `APPROVED` 后由系统**自动生成**标准合同草稿，服务商线上签至 `EFFECTIVE` 方可开展付费业务；agent **不是签约方**。
5. **材料前置**：真实资质在 agent 审核**之前**齐备提交，让第一闸口审真数据。

## 2. 模块化改造方案（按优先级）

### M1 — 关闭自服务入驻捷径  【P0】
- **改造目标**：消除任何人自助绕过审批成为服务商的安全缺口；保留"申请入驻"作为进入 QualificationApplication 流程的入口。
- **具体措施**：
  1. `POST /api/auth/apply-provider` 删除其"直接改 `role`"的副作用——改为仅创建 `QualificationApplication(kind:'provider', status:'FIRST_PENDING')`，不再改 `role`/`providerStatus`。或**整体下线该端点**，统一走 `POST /api/user/qualifications`（`user-console.controller.ts:1094`）。
  2. `POST /api/auth/submit-provider-review` 删除 `submitProviderReview`（自批 `APPROVED`）逻辑；该自助路径不再存在。
  3. `applyForProvider` / `submitProviderReview`（`auth.service.ts:153/209`）若保留作内部 helper，仅在 ADMIN 终审落地流程内调用，加注释与守卫，**绝不暴露在公开 HTTP 路由**。
- **实施步骤**：
  - 改 `auth.controller.ts:73/83`：移除公开路由，或加 `@Roles('ADMIN')` 并改为内部触发 QualificationApplication。
  - 改 `auth.service.ts:153/209`：去掉 `role`/`providerStatus` 直接赋值；如保留，仅服务 gated 流程。
  - 全仓 grep 确认 `apps/web` 的"申请入驻"UI 改调 `POST /api/user/qualifications`（而非 apply-provider）。
- **预期收益**：入驻唯一真源收敛，审批链不再被穿透；合规与欺诈风险大幅下降。
- **潜在影响/缓解**：消费端"一键成为服务商"入口失效 → 同步改 UI 文案为"提交入驻申请，等待审核"；影响范围小，无数据迁移。
- **优先级**：P0（阻断项，其他改造在其之上才有意义）。

### M2 — 修复归属（regionPath + agentId 写入）  【P0】
- **改造目标**：让服务商与代理商的归属从"隐式前缀软匹配 + 空字段"变为"显式、可校验、无歧义"。
- **具体措施**：
  1. 终审落地 `applyQualificationResult`（`user-console.controller.ts:1378`）provider 分支：将申请单 `regionPath` 写入 `User.regionPath`；按"最长前缀匹配"解析所属 AGENT 并写入 `User.agentId`。
  2. 注册阶段（`auth.service.ts register` ~`:60`）：要求 `regionPath` 必填（无则阻断或标记"待分配"）。
  3. seed / 存量数据回填：对已有 `regionPath` 但 `agentId=null` 的服务商，按同样前缀规则补写 `agentId`。
  4. schema 给 `User.regionPath` 加**约束**防止代理商店区重叠：`provider` 侧的归属用 `agentId` 作主键；代理商 `regionPath` 加 `@unique`（或 `role+regionPath` 唯一），杜绝重叠。
- **实施步骤**：
  - 改 `user-console.controller.ts:1378` 的 `user.update` data 块，加 `regionPath`、`agentId`。
  - 新增 `resolveAgentId(regionPath)` helper（取 `role:'AGENT'` 中 `regionPath` 为申请 `regionPath` 最长前缀且唯一者；多匹配/无匹配上报告警）。
  - 改 `schema.prisma:132` 加唯一约束；`prisma db push --skip-generate` 后重建 client。
  - 写一次性脚本回填存量 `agentId`（仅在 push 后跑）。
- **预期收益**：`GET /api/agent/providers` 与 `agentOf` 反向列表真实可用；消除孤主体/多归属歧义；前端可区分"硬归属"与"区域软匹配"。
- **潜在影响/缓解**：加唯一约束可能使种子/存量存在重叠时 push 失败 → 先审计 seed 辖区，确保无重叠再 push；回填脚本幂等、可重跑。
- **优先级**：P0（归属是整条管线正确的基础）。

### M3 — 材料前置（提交在 agent 一审之前）  【P1】
- **改造目标**：让代理商第一闸口审的是真实资质材料，而非空壳。
- **具体措施**：
  1. 将 `QualificationApplication` 的 `certNo`/附件/经营范围等**必填时机**从 `FIRST_PASSED 之后` 前移到"提交申请时"。
  2. `user-console.controller.ts:1432` 的顺序约束移除/改为"未填材料不允许进入一审"。
  3. 前端 `provider-review` 页顺序调整：先材料提交表单 → 再进入审核队列。
- **实施步骤**：
  - 改 `QualificationApplication` 字段必填校验（schema + 创建校验）。
  - 改 `user-console.controller.ts` 材料提交接口守卫逻辑。
  - 改 `apps/web` 入驻申请页与 `apps/admin` 资格审核页交互顺序。
- **预期收益**：第一闸口有效性恢复；降低造假穿透；与后续总台自动预检数据质量对齐。
- **潜在影响/缓解**：存量"已 FIRST_PASSED 但未补材料"的申请需补录或重走；需数据兼容处理。
- **优先级**：P1。

### M4 — 合同签约真实阶段 + 硬闸门  【P1】
- **改造目标**：合同成为"开展付费业务"的硬前置；签约流程经 API 可完整走到 `EFFECTIVE`。
- **具体措施**：
  1. **新增 `ProviderContract.create` 端点**（如 `POST /api/provider/contracts` 或并入终审落地）：总台 `APPROVED` 时由系统按预置模板**自动生成**草稿（`contractNo` `HT-YYYY-SPXXX`、`partyA` 填平台主体，**不填 agent**）。
  2. 补全 `signStage` 生命周期：`AWAIT_PROVIDER_SIGN → AWAIT_SENIOR_SIGN → APPROVING → EFFECTIVE`；新增推进到 `EFFECTIVE` 的端点（目前 `signContract` 止于 `AWAIT_SENIOR_SIGN`）。
  3. **合同即闸门**：服务商"上架付费供给"前置条件 = `providerStatus='APPROVED'` **且** 合同 `signStage='EFFECTIVE'`；未签仅可发免费供给。
  4. **agent 不入合同**：agent 侧合同保持只读（`agent-console.controller.ts:614` 不变）；若需分润，另签独立代理协议，不混入主合同。
  5. 合规电签：签署与 `idCard` 实名绑定，留存 PDF+时间戳+哈希；签约状态变更入 `auditLog`。
- **实施步骤**：
  - `schema.prisma:652` `ProviderContract` 评估是否补 `agentId?`（可选，仅用于路由展示，非签约方）。
  - 新增 create 端点 + 自动生成逻辑（在 `applyQualificationResult` APPROVED 分支触发或独立任务）。
  - 改 `provider-console.controller.ts:1898 signContract`：支持推进至 `EFFECTIVE`；新增总台确认签署端点。
  - 在"发布/上架付费供给"网关处加合同 `EFFECTIVE` 校验。
  - 前端 `apps/admin` 合同页加"创建/生成草稿/推进签署"动作；`apps/web` 补服务商侧合同签署页。
- **预期收益**：入驻闭环合规、可审计；法律风险收敛（agent 非签约方）；付费供给受控。
- **潜在影响/缓解**：需电签合规方案（可靠电子签名）；存量已签/在途合同需映射新状态机；改动面较大。
- **优先级**：P1。

### M5 — 总台自动化预检 + 分层人工审核  【P2】
- **改造目标**：在 ADMIN 终审阶段引入"风险预检 + 分层审"，既减负又防欺诈穿透。
- **具体措施**：
  1. 自动预检聚焦**风险信号**：重复 `certNo`/`idCard`、黑名单、格式、高风险类目、与已驳回主体相似度。
  2. **仅"干净且低风险"子集自动过**；高风险/首开/触发旗标者**强制人工审**。
  3. 保留 `reviewQualification`（`user-console.controller.ts:1333` @Roles('ADMIN')）人工终审 + `applyQualificationResult` 落地。
  4. 抽查作为**补充控制**：覆盖 agent 一审质量与总台自动通过项两端。
- **实施步骤**：
  - 新增 `preflightCheck(application)` 服务（在 `FINAL_PENDING` 进入人工/自动分流前调用）。
  - 在终审接口加 `autoApprovable` 判定；非可自动者标记 `FINAL_PENDING` 待人工。
  - 审计/抽样报表端点（轻量）。
- **预期收益**：总台负担真正下降且风险可控；自动化聚焦风险而非完整度。
- **潜在影响/缓解**：预检规则需迭代，初版宁可偏保守（多转人工）；避免"完整即过"的假自动化。
- **优先级**：P2。

### M6 — agent 审核质量护栏  【P2】
- **改造目标**：防止 agent 因利益激励（辖区 provider 数/流水挂钩）沦为橡皮图章。
- **具体措施**：建立 agent 审核质量 KPI / 逆向审计：抽查驳回准确率、漏检率、重复主体放行率；对异常 agent 触发复核。
- **实施步骤**：在 `AuditLog`（已有 `AGENT_QUALIFICATION_FIRST_REVIEW`）基础上加质量统计端点；前端 `agent` 工作台展示轻量看板（可选）。
- **预期收益**：第一闸口真实有效。
- **潜在影响/缓解**：仅报表/统计，无写权限变更，风险低。
- **优先级**：P2。

### M7 — 前端调整汇总  【P1/P2，贯穿】
- **改造目标**：UI 与后端新管线对齐。
- **具体页面**：
  - `apps/web`：入驻申请页改调 `POST /api/user/qualifications`（去 apply-provider）、材料表单前置、新增合同签署页。
  - `apps/admin`：`provider-review` / `agentQualifications` 顺序调整（材料前置）、`agent-console` 合同页新增"生成草稿/推进签署"、去掉 agent 作为签约方的任何表达。
  - `agent-console` 入驻审批列表（`agent-console.controller.ts:549`）加 `kind:'provider'` 过滤（修复 P-G），避免把 agent 类申请混入服务商名单。
- **实施步骤**：随 M1–M4 同步调整；i18n 补对应文案（遵循 `col.*`/`btn.*` 扁平键 + `pages.*` 嵌套对象规范，fallback `zh-CN`）。
- **预期收益**：端到端一致。
- **潜在影响/缓解**：多页面联动，需回归测试。
- **优先级**：随对应模块。

## 4. 实施顺序建议（里程碑）

- **阶段一（安全 + 归属基线）**：M1 → M2。先做，因为它堵住活漏洞并打下归属基础；其他改造在其之上才有意义。
- **阶段二（流程 + 合同）**：M3 → M4 → M7（对应部分）。材料前置 + 合同真实阶段 + 硬闸门。
- **阶段三（自动化 + 护栏）**：M5 → M6。总台风险预检 + agent 质量护栏（轻量、可后置）。

> 每一阶段独立可提交、可验证；建议阶段一完成即提交一次，避免大爆炸式改动。

## 5. 风险与回滚

- **schema 唯一约束**：push 前先审计 seed/存量辖区重叠，否则 push 失败；可先以"软校验 + 告警"过渡，再升硬约束。
- **自服务下线**：消费端入口改文案，避免用户困惑；保留 QualificationApplication 入口兜底。
- **合同状态机迁移**：存量合同映射新 `signStage` 需脚本；建议新字段/枚举向后兼容。
- **回滚**：每阶段独立 commit；后端改源码需 `build:compiled` 后 kill `:3000` 让 watchdog 拉新；回滚即回退对应 commit 并重建。
