## 二、安全问题（按严重程度分级）

### 🟠 中危（Medium）

#### M1. 注册接口接受并写入未经验证的权威 `regionPath`（权限边界污染）
- **位置**：`apps/server/src/auth/auth.service.ts` `register()`（约 L71–86）、`apps/server/src/auth/dto/auth.dto.ts` `RegisterDto.regionId`（L32–34）、`apps/web/src/api/client.ts` `register()` extra 签名
- **成因**：`register()` 在 `dto.regionId` 存在时，将其解析出的 `regionPath` 直接写入 `User.regionPath`。而 `User.regionPath` 在系统内被用于**访问控制判定**（`visibleToUser` 的 `REGION` 作用域、`resolveTarget` 辖区校验、代理商辖区统计）。
- **潜在影响**：调用方若主动传入 `regionId`，可**自我断言**一个 `regionPath`，从而
  1. 拓宽自身可见的 `REGION` 作用域消息（信息泄露面扩大）；
  2. 在代理商辖区统计/归属判定中人为改变归属基数。
  - **当前可达性**：web 端 `Register.tsx` 调用 `register()` 时**未透传 `regionId`**（仅传 `intent`/`realName`），故该路径当前 web 流程不触发；但服务端 API 仍接受该参数，属于潜在攻击面（任何直接调用 API 或未来客户端均可触发）。
- **最小化修复**（保持架构不变）：
  - 从 `register()` 删除 `regionId → regionPath` 的写入；若需保留"意向区域"，另存为非权威字段（如 `preferredRegionPath`），且**绝不**参与任何访问控制。
  - 同步从 `RegisterDto` 移除 `regionId`（或标注为纯引导、不落库）。
  - 与之相关：`applyForProvider` 中 `regionPath: user.regionPath ?? null` 的注入一并移除（见 M2）。

#### M2. `apply-provider` 把（注册自填/空）`regionPath` 注入入驻申请基线，影响代理商归属判定
- **位置**：`apps/server/src/auth/auth.service.ts` `applyForProvider()`（约 L208–212）
- **成因**：`applyForProvider` 创建申请时 `regionPath: user.regionPath ?? null`。虽然 web 正式入口 `POST /api/user/qualifications`（`createQualification`）以表单 `regionPath` 覆盖，但 `apply-provider` 作为仍开放的快捷入口，会让申请的 `regionPath` 源自一个**未经管理员核验**的值；而终审 `applyQualificationResult()` 正是以 `app.regionPath` 做**最长前缀匹配代理商**并固化归属。
- **潜在影响**：若走 `apply-provider` 路径，代理商归属可被非核验值影响。当前 web 走 `createQualification`（表单 regionPath，管理员可见可审）已规避，但 `apply-provider` 端点仍对**任意已登录用户**开放。
- **最小化修复**：`applyForProvider` 不再从 `user.regionPath` 注入，改为 `regionPath: null`；或显式将 `apply-provider` 标记为废弃、统一收敛到 `createQualification`。

#### M3. JWT 密钥存在硬编码开发回退值（生产可伪造令牌）—— 既有项，投产前必改
- **位置**：`apps/server/src/auth/auth.module.ts:13`、`auth.service.ts:115/505`、`strategies/jwt.strategy.ts:39`
- **成因**：`secret: process.env.JWT_SECRET ?? 'h5design_jwt_secret_dev'`（refresh 同理）。
- **潜在影响**：若生产环境未配置 `JWT_SECRET`，任何人都可用该可预测密钥**伪造 ADMIN 令牌**，造成完全的身份认证绕过。属"配置即沦陷"的高影响项。
- **最小化修复**：生产环境（`NODE_ENV=production`）启动时若缺失 `JWT_SECRET` / `JWT_REFRESH_SECRET` 直接抛错退出；绝不保留默认回退。

#### M4. 限流守卫基于内存 Map 且未信任代理 IP（集群/反代下失效）
- **位置**：`apps/server/src/common/guards/rate-limit.guard.ts`、`main.ts`（缺少 `app.set('trust proxy', …)`）
- **成因**：`req.ip` 在未启用 trust-proxy 时取到的是直连对等地址；计数器为**单实例内存 Map**。
- **潜在影响**：在反向代理 / 负载均衡 / 多实例部署下：
  - 所有客户端被视为同一 IP → 限流误伤或**完全失效**（无法按真实客户端限流）；
  - 多实例间计数不共享，爆破/滥用防护被绕过。
- **最小化修复**：若部署在代理后，启用 `app.set('trust proxy', 1)` 并安全解析 `X-Forwarded-For`；多实例改用 Redis 共享计数（守卫注释已自承此限制）。

### 🟡 低危（Low）

#### L1. CORS 配置过于宽松
- **位置**：`main.ts:14` `app.enableCors()`（无参数）
- **成因**：默认反射任意 `Origin`，无白名单。
- **影响**：Bearer-Token 接口风险有限（无 Cookie 自动携带），但仍允许任意站点在受害者浏览器上下文中发起带令牌的 XHR；建议显式 `origin` 白名单。

#### L2. 并发注册竞态：check-then-create 无事务、无 P2002 兜底
- **位置**：`auth.service.ts` `register()`（约 L62–94）
- **成因**：先 `findUnique` 判重再 `create`，中间无事务；`phone` 为 `@unique`，DB 可防重，但并发同号时败者会抛未捕获的 `P2002` → 500（而非 409）。
- **影响**：极端并发下败者收到 500；因唯一约束在，不会产生重复账号，无数据损坏。建议 `create` 包 `try/catch`，命中 `P2002` 转 `ConflictException`。

#### L3. 合同推进端点 `advanceContract` 在 `stage` 缺失时静默落 `EFFECTIVE`（付费闸门旁路）
- **位置**：`apps/server/src/console/provider-console.controller.ts` `advanceContract()`（L1955–1991）
- **成因**：`@Body()` 为无校验裸对象；当 `stage` 省略时，代码走 `EFFECTIVE` 分支（跳过了 `APPROVING`）。端点受 `@Roles('ADMIN')` 保护，风险为**前端/调用方漏传 `stage` 即直接打开付费闸门**。
- **影响**：防御纵深缺口。建议用 `@IsIn(['APPROVING','EFFECTIVE'])` 的 DTO 校验，缺省/非法即 400。

#### L4. 敏感字段 `idCard` 回传运营端（代理商可见用户身份证号）
- **位置**：`apps/server/src/admin/admin.service.ts` `userDetailSelect` 含 `idCard: true`（L49），端点 `@Roles('ADMIN','AGENT')`
- **成因**：详情接口返回完整身份证号给管理员/代理商。
- **影响**：隐私面；若运营端存在 XSS 即泄露。当前已确认**普通用户端不返回 `idCard`**（已核对 `user-console.controller` 无 `idCard: true`）。建议列表脱敏、仅详情按需展示。

#### L5. 反馈/订单中其他用户 `phone` 回传
- **位置**：`user-console.controller.ts` L356（`buyer.phone`）、L537–538（`reporter/target.phone`）
- **成因**：业务数据中携带对方手机号。
- **影响**：轻微信息暴露，多为业务必需；建议评估是否前端按需展示。

#### L6. 密码最小长度仅 6 位，无复杂度要求
- **位置**：`auth/dto/auth.dto.ts` `RegisterDto.password` `@MinLength(6)`
- **成因**：弱下限。bcrypt cost=10 + 限流可缓解，但仍偏弱。
- **建议**：提升至 `@MinLength(8)`，可选复杂度规则（低优先）。

#### L7. `certNo` 唯一性仅应用层校验，无 DB 唯一约束（TOCTOU）
- **位置**：`schema.prisma` `QualificationApplication.certNo` 仅 `@@index`，非 `@unique`；`createQualification` check-then-create
- **成因**：并发同号在途申请可同时越过"已入驻(APPROVED)拦截"并各建一条；但终审时对已 APPROVED 者会再次拦截，故被**终审环节缓解**。
- **建议**：低优先；如需彻底消除重复在途单，可加部分唯一索引或在审批侧做幂等。

## 三、已核对无误 / 安全良好的部分（结论）

以下为本次重点核查项，**未发现可利用问题**，予以确认：

1. **注册越权字段注入（不可提权）**：`RegisterDto` 仅含 `phone/password/nickname/realName/regionId/intent`，**无 `role`/`providerStatus`/`points`/`agentId`**。运行时探针确认在注册体注入 `role:'ADMIN'`、`providerStatus:'APPROVED'`、`points:999999`、`agentId:'x'` 均被忽略，账号仍以 `USER` 落地。✅
2. **密码存储**：统一使用 `bcrypt.hash(pwd, 10)` 加盐哈希，登录/改密用 `bcrypt.compare`；**无明文、无 MD5/SHA 弱哈希、无自定义弱加密**。✅
3. **自服务提权通道已关闭**：原 `submit-provider-review`（自助把 `providerStatus` 置 APPROVED）已移除；`applyForProvider` 仅建申请，身份变更唯一真源收敛到总台终审 `APPROVED`。✅
4. **重提溯源越权防护**：`resubmitOfId` 严格校验 `userId === 当前用户` 且原单状态为 `REJECTED/WITHDRAWN`、层次一致，杜绝代他人重提。✅
5. **代理商一审作用域收窄**：`reviewQualification` 强制 `app.regionPath.startsWith(agent.regionPath)`，无辖区配置直接 `Forbidden`；状态机限定仅 `FIRST_PENDING` 可一审。✅
6. **普通用户代建防护**：`resolveUserId` 对 `USER` 角色强制取自身 `id`，忽略 `body.userId`；无 IDOR 创建他人申请。✅
7. **证件号重复入驻拦截**：对已 `APPROVED` 主体直接 `400` 拦截；对在途申请打 `DUPLICATE_CERT_NO` 旗标交人工。✅
8. **代理商辖区校验**：深度必须到区县（regionPath 三级）、且与既有代理商重叠预检前移。✅
9. **XSS**：全仓未使用 `dangerouslySetInnerHTML` / `innerHTML`。✅
10. **密钥不入库**：`apps/server/.env` 已被 git 忽略，无密钥泄露。✅
11. **注册/登录/申请/改密均挂载了速率限制**（`RateLimitGuard`，如 register 5/分钟）。✅
12. **前端令牌存储**：令牌存 `localStorage`（SPA 常规做法），错误日志仅 `import.meta.env.DEV` 下打印且不含密码/令牌明文。✅

## 四、UI/UX 视角简核（ui-ux-design-pro）

- 注册页密码字段 `type="password"`、确认密码二次校验、`passwordMismatch` 提示齐备，无明显 UX 安全反模式。✅
- `Onboarding` / `Apply` 区域选择采用"逐级下钻到区县"的交互，与服务端三级校验一致，避免用户误填超大辖区。✅
- 建议（非阻塞）：注册/入驻表单对"证件号码、手机号"做前端格式预校验与脱敏展示（如详情页身份证中间掩码），降低敏感信息在界面上的暴露时长。
