## 1. 分层设计与核心原则

```
占位符注册表（运营端独占写，配置真相源）
   │  key / label(单语言内容) / type / required / hint / defaultValue / status / scope
   ▼
绑定实例（模板级 / 项目级覆盖：必填覆盖、可见覆盖、默认值覆盖）
   │  el.binding.key = placeholder.key（底层不变）
   ▼
渲染内核（personalizeSchema 按 key 替换，零改动）
```

> 多语言策略：注册表只存**单语言内容**（`label`/`hint`/`defaultValue` 纯文本，按当前语言环境录入）；
> 界面框架文案（字段名/按钮/标题/提示）一律由**系统 i18n**（`t()`）按当前语言渲染，不在界面内维护多语言文本。详见 §7。

原则（据此收口"隐式创建变量"风险）：
- **编辑器只绑定、不创建**：新建占位符只在运营端注册表完成；编辑器下拉仅列已注册项（按对象类型过滤）。
- **定义 / 实例分离**：注册表存"定义"（含默认必填/默认可见）；模板或批次可覆盖必填与可见。
- **注册表为空时回落旧逻辑**：绝不阻断现有创作与渲染。

## 2. 数据模型（新增 Prisma 模型 `PlaceholderRegistry`）

```prisma
model PlaceholderRegistry {
  id          String   @id @default(cuid())
  key         String   @unique   // ASCII 稳定 key，如 groom / bride / weddingImg1 / weddingDate / weddingAddr
  type        String              // 'text' | 'image' | 'datetime' | 'address'
  label       String              // 占位符显示名（单语言内容，按当前语言环境录入；不存多语言）
  hint        String   @default("") // 编辑提示（单语言内容）
  defaultValue String   @default("") // 默认值（单语言；datetime/address 存格式化串或原始值）
  scope       String   @default("batch") // 见 §6：'record'(名单字段) | 'batch'(批次常量)
  requiredDef Boolean  @default(false)  // 注册表级默认必填；可被绑定实例覆盖
  status      String   @default("visible") // 'visible' | 'hidden'
  legacy      Boolean  @default(false)  // 老 GUEST_FIELD_DEFS / ext_ 迁移标记
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt
}
```

- **不新建"变量"表**（变量 = `binding.key`，真值在 schema，沿用既有铁律）。
- 迁移按项目铁律手写 `migration.sql` → `prisma db execute` → `migrate resolve --applied` → `prisma generate`。

## 6. 关键缺口：占位符的作用域（必须补的设计）

当前 `personalizeSchema` 只从 `record.data`（**每条名单记录**）取数。但你方案里的
**婚礼日期 / 地址 / 婚庆图片** 是**批次级常量**（一次设置、整套请柬共用），并非名单字段。

- [ ] 注册表 `scope` 字段区分两类占位符：
  - `'record'`（名单字段型）：宾客丈夫/妻子/姓名/称谓/性别/单位/桌号/手机号/备注/ 自定义字段→ 仍从 `record.data` 取（底层即 guest 字段或 `ext_` 字段）。
  - `'batch'`（批次常量型）：新郎/新娘、邀请人丈夫/妻子、邀请内容、婚礼日期/时间、地址、婚庆图片 → **不从名单取**，由用户在创建模板或批量生成时一次性填写。
- [x] 落地方式（二选一，建议 A）：
  - **A**：批量生成表单按 `scope` 分组渲染——`record` 型走名单列映射，`batch` 型走独立"批次常量"输入区；提交时把 `batch` 值注入每条记录的 `data` 同名字段（`personalizeSchema` 无需改）。
  - **B**：内核新增 `batchValues` 维度，`personalizeSchema` 取值链增加 `record.data → batchValues → fallback`。
- [x] 老 `ext_` 自定义字段若为批次常量，迁移时统一标记 `scope='batch'`。

## 7. 多语言方案（系统 i18n 管理机制）

> **策略变更**：原方案在注册表内为每个占位符维护 `labelI18n / hintI18n / defaultI18n` 三套 6 语言 JSONB（运营端对话框以 3×6 网格逐语言录入）。
> 现改为「**单语言内容录入 + 系统 i18n 框架文案**」，理由：界面不应直接维护多语言文本，UI 语种须与当前语言环境严格对齐、禁止混语。

- [x] **UI 框架层（系统 i18n）**：对话框 / 列表 / 编辑器侧栏 / 聚合面板的所有界面文案（字段名、按钮、区块标题、提示语、空态）一律走系统 `t()` 机制，按当前语言环境渲染，**绝不混语**。
- [x] **内容层（单语言录入）**：占位符的 `label` / `hint` / `defaultValue` 为**单一语言**内容，由管理员在**当前语言环境**下一次录入；对话框**不再提供"多语言标签"网格**，hint / default 去多语言、仅留单语言输入。
- [x] 存储：移除 `labelI18n / hintI18n / defaultI18n` JSONB，改为 `label String` / `hint String` / `defaultValue String` 纯文本列（见 §2）。
- [x] 展示：`label` 直接取该单语言字段展示；若该占位符由另一语言环境录入，则展示那次录入的语言文本——但**界面框架文案始终与当前语言对齐**，不会出现"界面中英混排"。
- [x] 日期 / 地址格式化串（`defaultValue`）按当前语言环境录入的单语言串即可；地区格式化逻辑（渲染时套用）见 §5。
- [x] 若未来需要内容级多语言，应通过**系统 i18n 的 key 映射**（在 i18n 资源文件中维护），而非在占位符对话框内逐字段维护——**不在界面中直接维护多语言文本**。

## 9. 实施顺序（分阶段，每阶段可独立交付 / 回滚）

- **Phase A（真相源先立）**：数据模型 + 服务端 CRUD + 运营端菜单/详情页 + seed 老字段。
- **Phase B（编辑器接注册表）**：下拉读注册表 + 类型过滤 + 绑定状态/错误提示；默认保留旧逻辑回落（灰度）。
- **Phase C（scope + 单语言化 + 地区格式化）**：批次常量型占位符表单分组、`datetime/address` 地区格式化；将运营端对话框 / 编辑器 / 聚合面板的占位符相关 UI 统一收口为「单语言内容录入 + 系统 i18n 框架文案」，移除多语言 JSONB 维护（见 §7、§12）。
- **Phase D（收尾）**：老数据迁移校验、文档、验收脚本。

## 11. 明确不改 / 保留项
