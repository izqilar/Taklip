## 一、被测方案与关键事实（验收基线）

### 1.1 方案形态（据评估文档）
- 编辑器文本对象属性面板「组件别名（真身为 `BaseElement.name`，见 `packages/core/src/schema.ts:217`，与 `alias` 共用同一中文标签，见记忆 `2026-10-09` 阻断级事实）」旁加「设为变量」复选框 → 勾选后该元素获得 `ElementBinding`（`:224`），`key` 由 slug 生成器产出（ASCII，永不变），`name` 为人类可读别名。
- 批量生成时选模板 + 名单 → 弹出映射对话框，用户指定「名单字段 ↔ 变量」绑定（方案 D 在生成期做元素级绑定）。
- **否决 Scheme A 裸 alias（P0）**：`personalize.ts:179` 的 `TOKEN_RE = /\{\{\s*([a-zA-Z_][a-zA-Z0-9_]*)\s*\}\}/g` 仅匹配 ASCII，**中文变量名会原样打印成 `{{新人姓名}}`**。因此变量 `key` 必须为 ASCII slug，人类可读 `name` 挂 `binding.name`。
- 判定逻辑（三级阻断 / 疑似度打分 `scoreVariableCandidate` / slug 生成 / 位置描述 `describeElementPosition`）全部放在 `packages/core` 纯函数，三端与服务端共享（架构评估 §3.4、§8）。

## 二、验收方法与标注约定

- **每条用例含**：前置条件 / 步骤 / 预期 / 断言。
- 标注：`auto` = 可自动化（core 纯函数单测 / 服务端集成测试 / e2e 脚本）；`manual` = 需人工 UI 走查或截图判定。
- **auto 优先**：core 纯函数、服务端 `getHealth`/`saveMapping`/`batchGenerate`/`runJob`、渲染产物 HTML/文本断言尽量自动化；画布点选交互、RTL 镜像、跨端视觉一致性用 `manual` + 截图存档。
- **断言载体**：渲染产物断言优先扫描 **导出 HTML / 文本流**（或出图 sha1 变化），而非仅 UI 文案。
- 数据规模基线：名单总数 49，其中约 **21/49（43%）** 列定义（`columnDefs`）缺失（拍板清单口径；注：2026-10-09 DB 扫描报 33/49，无论哪版，兜底须保证 **≥95% 名单可用**，见 MVP 标准②）。

## 三、MVP 三条硬标准（最高优先级）

### 用例 M-1：普通用户无需理解变量定义即可完成绑定（解耦命名与字段绑定）
- **前置**：新注册用户（无文档）；模板含 2 个变量元素（key=slug，name=`新人姓名`/`新娘姓名`）；维文模板；名单列为 `husband_name`/`wife_name`。
- **步骤**：
  1. 进入生成对话框，系统自动给出映射建议（同名/同义猜测并标「已猜测，请确认」）。
  2. 用户仅点选「确认」，**不输入任何变量 key / 不进编辑器**。
  3. 生成。
- **预期**：生成的请柬上维文姓名处正确替换为名单 `husband_name`/`wife_name` 值；用户全程**未接触 ASCII slug / `binding.key` 概念**。
- **断言**：`auto` — 调 `personalizeSchema`，断言输出文本 = 名单值；`collectBindings` 聚合视图 `key` 为 ASCII slug、`label` 为人类可读名。`manual` — 用户走查问卷确认「无需看文档」。

### 用例 M-2：零绑定存量模板（104/108 之一）指认一次即生效（老板原始诉求）
- **前置**：取一个 `draftSchema ?? schema` 零绑定模板（如 `cmujnp4no000plmgu7dmf0anv` 类）；名单 `Male=ZZTEST99`/`Female=李四`。
- **步骤**：
  1. 不进编辑器、不预标记。
  2. 生成对话框里**点选**夫妻姓名元素 → 指认 `Male`/`Female` 列（方案 D 生成期绑定）。
  3. 改名单值（`Male`→新值）→ 重新生成。
- **预期**：出图**确实变化**（图像 sha1 改变，非恒定 `61c10f44c7da`）；姓名元素解析为新值（如 `ZZTEST99 & 李四` 变）。
- **断言**：`auto` — 首渲 sha1 ≠ 再渲 sha1；`personalizeSchema` 输出姓名元素 = 新名单值。`manual` — 截图对比前后两张图。

### 用例 M-3：模板 `draftSchema`/`schema` 逐字节未变（防回写模板老路）
- **前置**：同 M-2 的零绑定模板。
- **步骤**：完成 D 生成期绑定 + 多次重生成。
- **预期**：模板存储的 `draftSchema`/`schema` 未被任何生成操作改写。
- **断言**：`auto` — 生成前后 `JSON.stringify(template.draftSchema ?? template.schema)` 完全一致；`binding` 写入**项目侧**（project 级 `elementBindings`/`variableMapping`），不回写模板（架构评估 §3.4：D 落点为 project 而非模板）。

### 用例 M-4（补充 S5 ⑨）：`superseded[].autoApplied=true` 且出图不丢内容
- **前置**：模板变量 key 与名单列经自动猜测已匹配。
- **步骤**：生成 → 检查 superseded 列表。
- **预期**：自动应用的映射 `autoApplied=true`；出图元素数量、文本数量与模板一致（不丢块）。
- **断言**：`auto` — 断言 `superseded.every(x=>x.autoApplied===true)`；渲染结果 DOM 节点数 ≥ 模板节点数（仅变量替换，无整块消失，除非 D2 整段变量空值隐藏且已显式确认）。

### 用例 M-5（补充 S5 ⑩）：绕过 health 直连 `batch-generate`（admin 现状）同样不劣化
- **前置**：admin 两端（`UserInvitationCenter`/`spInvitationBatch`）现状直连 `batch-generate`、无 health 环节。
- **步骤**：以 admin 路径（不调 `getHealth`）走完整生成。
- **预期**：兜底发生在**渲染侧**（`personalizeSchema`/`deriveColumnsFromRecords`）而非 UI 侧；产物与 web 端一致、不劣化。
- **断言**：`auto` — 不调 `getHealth` 直接 `batch-generate`，断言渲染产物变量正确替换、无 `{{...}}` 残留。

## 四、三级阻塞判定（A1，产品评估 §5.4.1）

> 核心原则：**「名单某行值为空」≠「变量根本没建映射」**。前者数据问题（D2 隐藏合理，不阻断）；后者配置问题（必须拦截），否则重演 104/108 静默错误。

### 用例 B-1（硬阻断 1）：变量数>0 且已映射=0 → 红条阻断
- **前置**：模板含 ≥1 变量；映射对话框打开，用户未做任何绑定。
- **步骤**：尝试点「生成」。
- **预期**：🔴 红条「你还没有指定任何对应关系，生成的请柬将不含名单信息」；保留「跳过，生成统一版式」显式出口（二次确认后才放行）。
- **断言**：`auto` — `classifyHealth`（core 纯函数）返回 `{level:'block', kind:'NO_MAPPING_AT_ALL'}`；`getHealth` 响应 `blocked=true`。`manual` — UI 红条 + 出口按钮可见。

### 用例 B-2（硬阻断 2）：`binding.required===true` 的变量未映射
- **前置**：某变量 `binding.required=true` 且未映射。
- **步骤**：尝试生成。
- **预期**：🔴 红条标出该项（按 `required` 而非旧的 `critical: v.key==='guest_name'`，见风险 R-2）。
- **断言**：`auto` — 断言 `critical` 字段由 `binding.required` 推导，而非 key 字符串比较。

### 用例 B-3（硬阻断 3）：名单完全无可用列
- **前置**：名单 `columnDefs` 为空 **且** 记录也无任何 key（`deriveColumnsFromRecords` 返回空）。
- **步骤**：尝试生成。
- **预期**：🔴 红条「该名单没有任何列可映射」。
- **断言**：`auto` — `deriveColumnsFromRecords([])` 返回 `[]` 时 `classifyHealth` 返回 `block`；`getHealth.blocked=true`。

### 用例 B-4（琥珀确认）：部分未映射（已映射≥1）
- **前置**：3 个变量，用户只映射了 1 个；其中某已映射变量在 5/12 行值为空。
- **步骤**：尝试生成。
- **预期**：🟡 琥珀确认，逐项列出「这些位置将留空/隐藏，共 N 张」并附张数（复用 `emptyHits`）。放行。
- **断言**：`auto` — `classifyHealth` 返回 `{level:'warn', kind:'PARTIAL_MAPPING', affectedRows:N}`；响应含 `emptyHits` 行数。

### 用例 B-5（放行）：全部映射 / 空值
- **前置**：全部变量已映射；某行值为空（数据问题）。
- **步骤**：生成。
- **预期**：🟢 放行。空值按 D2：整段变量元素 `visible=false`（隐藏），混合文案空令牌留空串（不隐藏）。**不阻断生成**。
- **断言**：`auto` — `personalizeSchema` 输出中，整段变量空值元素的 `visible===false`；混合文案元素保留前后缀且 `visible` 不变。`getHealth.blocked=false`。

## 七、中文变量名陷阱（Scheme A 否决项，P0）

> 强制约束：变量 `key` 必须为 ASCII slug。若实现错误地把中文「组件别名」当 `key`，渲染产物不得出现 `{{新人姓名}}` 字面量。

### 用例 C-1：误用中文别名作 key → 渲染产物不得含 `{{新人姓名}}`
- **前置**：构造一个**反例** schema，某文本元素 `binding.key='新人姓名'`（中文）且 text 含 `{{新人姓名}}`。
- **步骤**：`personalizeSchema` 渲染该 schema（名单无 `新人姓名` 列）。
- **预期**：`TOKEN_RE` 不匹配中文 → `applyTokens` 原样保留 `{{新人姓名}}` → **这正是要杜绝的错误形态**。本用例用于**监控回归**：正确实现下，key 必为 slug（如 `v_8f3a1c`），`applyTokens` 能匹配 `{{v_8f3a1c}}` → 产出真实值，无 `{{...}}` 残留。
- **断言**：`auto` — ① 断言生产路径下 `ElementBinding.key` 经 slug 生成器产出、`/^[a-zA-Z_][a-zA-Z0-9_]*$/.test(key)===true`；② 渲染产物（HTML/文本）`NOT match /\{\{[^}]+\}\}/`（无未替换令牌）；③ 若以中文 key 注入测试，`personalizeSchema` 输出 text 仍含 `{{新人姓名}}`（证明该形态被拦截，非被「吃掉」）。

### 用例 C-2：`{{token}}` 与 slug key 共存
