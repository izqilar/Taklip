## 1. 项目概述

### 1.1 背景

平台现有四个**平台身份**：`USER`（消费者）、`SERVICE_PROVIDER`（服务商）、`AGENT`（代理商）、`ADMIN`（总台）。随着业务开展，三个组织层（总台 / 代理商 / 服务商）都需要调度自己的员工处理日常业务——例如服务商视角已有「我的团队」模块，可通过「新建团队成员」建立员工。

**问题**：员工的「团队角色」目前是一个自由文本输入框，没有任何权限含义。

### 1.2 核心问题

| 编号 | 问题 | 影响 |
|------|------|------|
| P-01 | 「团队角色」是自由文本，可填「花艺师」也可填「asdf」 | 无法按岗位调度，无法统计，无法约束 |
| P-02 | 员工记录与 `User` 无任何关联 | 员工不能登录，岗位只是「通讯录标签」 |
| P-03 | `funcPerms` / `dataScope` 已落库但服务端零消费 | 权限字段是摆设，填了也不生效 |
| P-04 | 工种（会什么手艺）与岗位（能管什么事）混在一个字段 | 「服务类型=摄影摄像」又填「花艺师」，语义打架 |
| P-05 | 代理商、总台完全没有内部员工模块 | 这两层将来无法调度自己的员工 |
| P-06 | 权限串漂移成 3 份，其中一份是零调用死代码 | 后续做门控时真相源不明 |

### 1.3 目标与非目标

**目标（本轮 P0）**

| 编号 | 目标 |
|------|------|
| G-01 | 三个组织层各有明确的**内置岗位池**，岗位可选可自填（AutoComplete） |
| G-02 | 岗位自动带出**职责池**，切换服务类型时联动重置 |
| G-03 | 岗位绑定**功能权限子集**（从已有 28 个权限点中取子集，复选框勾选） |
| G-04 | 岗位绑定**数据范围**（按层不同：self / service / provider / region / agent / all），服务端白名单校验 |
| G-05 | 用一张通用表 `OrgStaff` 承载三层，避免三套表 |
| G-06 | 后端补 DTO 校验 + 停用接口（PATCH），消除 `body: any` 与无白名单现状 |

**非目标（P1 及以后）**

- 员工登录与真实鉴权门控
- 权限串三份收敛（删死代码、加别名映射）
- 审计时间线可视化

### 1.4 概念定义（务必区分）

| 概念 | 含义 | 例子 | 承载字段 |
|------|------|------|---------|
| **平台身份** | 决定「进哪个端、管哪个辖区」 | 服务商 / 代理商 / 总台 | `User.role`（不动） |
| **组织内岗位** | 决定「在本单位能干什么」 | 客服专员 / 店长调度 / 财务专员 | `OrgStaff.staffRole` |
| **工种（服务类型）** | 决定「会什么手艺」 | 摄影摄像 / 花艺布置 / 司仪主持 | `OrgStaff.serviceType` |
| **职责** | 岗位的具体工作项，由岗位池自动带出 | 拍摄执行 / 后期制作 / 客户沟通 | `OrgStaff.duties` |
| **功能权限** | 可执行的操作点，从 28 点中取子集 | `order:handle` / `data:export` | `OrgStaff.funcPerms` |
| **数据范围** | 可见数据的边界 | 自身 / 本服务商 / 本辖区 | `OrgStaff.dataScope` |

> **关键澄清**：`工种 ≠ 岗位`。「花艺师」在原型中是**服务类型下的角色名**，但它本质上描述的是手艺归属；本规范把它归入「岗位池」，同时保留「服务类型」字段表达手艺，两者通过 `TEAM_SVC_META` 联动，不再各说各话。

### 2.2 三个必须处理的冲突

#### 冲突 1：原型「婚庆策划」vs 代码「婚礼策划」

原型 `TEAM_SVC_META` 定义 6 个服务类型，代码 `SVC_OPTIONS` 有 15 项：

| 原型 TEAM_SVC_META（6） | SVC_OPTIONS（15）中是否命中 |
|---|---|
| 特约设计 | ✅ 命中 |
| 婚庆策划 | ❌ 代码里叫「**婚礼策划**」，名字对不上 |
| 摄影摄像 | ✅ 命中 |
| 花艺布置 | ✅ 命中 |
| 司仪主持 | ✅ 命中 |
| 灯光音响 | ✅ 命中 |

**结论**：15 项中仅 **5 项命中**，另 **10 项**（插花礼仪、乐队演出、礼仪执事、主持人、婚庆主持、宴会设计、化妆造型、司仪培训、婚礼策划、光影纪录）需要 **fallback 默认岗位池**，否则下拉为空。
**处理**：`teamRolesOf(serviceType)` 未命中时返回 `TEAM_DEFAULT_ROLES`；「婚礼策划」加别名映射到「婚庆策划」的岗位池。

#### 冲突 2：种子数据已存自由文本

`apps/server/prisma/seed-provider-view.js` 中存量 `ProviderTeamMember.teamRole` 是自由文本（如「花艺师 / 客服专员」这种带斜杠的复合值）。

**结论**：岗位控件**必须用 AutoComplete（可选也可自填）**，不能用严格 `Select`——否则存量值不在选项池内会显示为空。
**处理**：AutoComplete + `filterOption` 支持联想；自填值放行，但服务端记录为「自定义岗位」。

#### 冲突 3：员工权限不能取「∩ 雇主权限串」

`auth.service.ts:270-288 getAccess()` 中 `SERVICE_PROVIDER` 只有 4 项：`feedback:read` / `feedback:own` / `message:read` / `message:own`，**不含 `order:*`**。

**结论**：若按「员工权限 = 岗位权限 ∩ 雇主已授予权限串」计算，结果**恒为空**。
**处理**：P0 只声明岗位权限、**不做门控**；P1 改为「雇主**可用权限域**白名单」推导（由 `serviceRoles` + `providerStatus` 推导，而非取已授予串的交集）。

## 3. 角色模型设计

### 3.1 双轴模型

```
┌──────────────────────────────────────────────────────────┐
│  平台身份 User.role（USER / SERVICE_PROVIDER / AGENT / ADMIN）  │
│      决定：进哪个端、管哪个辖区            ← 本轮不动          │
└───────────────────────┬──────────────────────────────────┘
                        │  ×
┌───────────────────────▼──────────────────────────────────┐
│  组织内岗位 StaffRole                                      │
│  ┌────────────┐ ┌──────────────┐ ┌──────────────────┐   │
│  │ 岗位池      │ │ 功能权限子集  │ │ 数据范围          │   │
│  │ 内置+自填   │ │ 28点取子集    │ │ self/service/... │   │
│  └────────────┘ └──────────────┘ └──────────────────┘   │
└───────────────────────┬──────────────────────────────────┘
                        │  ↓
┌───────────────────────▼──────────────────────────────────┐
│  生效权限 = 岗位功能权限 ∩ 雇主可用权限域 ∩ 数据范围        │
│  （P1 才门控；P0 仅声明，不参与鉴权）                      │
└──────────────────────────────────────────────────────────┘
```

### 3.2 为什么不为员工新增平台角色

曾考虑给员工加 `STAFF` 角色，但会冲击：`ROLE_HOME`（`auth.service.ts:30-35`）、`canSeeByRole`（`accessControlProvider.ts:38-63`）、`getAccess`（`:270`）、`RolesGuard`、`DataScopeInterceptor` 全线。

**决策**：员工沿用现有 `USER` 平台身份，靠「组织成员关系」提权（P1 落地）。

### 3.3 为什么不用 `subject` 机制

`subjectId(req, subject)`（`provider-console.controller.ts:66-67`）是 **ADMIN 视察他人**且纯客户端可信、不校验归属；员工是**自登录**主体，语义完全不同。

**决策**：不复用。P1 另起：JWT payload 扩 `sid` / `org`（现为 `{sub, phone}`），`DataScopeInterceptor` 增加组织分支。

## 4. 数据模型设计

### 4.1 新增 `OrgStaff`（一表统三层）

```prisma
// 组织内员工（一表承载 服务商 / 代理商 / 总台 三层内部成员）
model OrgStaff {
  id            String   @id @default(cuid())
  orgType       String   @map("org_type")    // PROVIDER | AGENT | CONSOLE
  orgId         String   @map("org_id")      // 服务商/代理商 id；CONSOLE 固定 "console"
  memberNo      String   @unique @map("member_no")  // MT-XXXX
  name          String
  phone         String
  accountStatus String   @default("ACTIVE") @map("account_status") // ACTIVE | PENDING | DISABLED
  serviceType   String?  @map("service_type")   // 仅 PROVIDER 层使用（工种）
  staffRole     String   @map("staff_role")     // 岗位（可自填）
  duties        String[] @default([])           // 职责
  funcPerms     String[] @default([]) @map("func_perms")  // 功能权限子集
  dataScope     String   @default("self") @map("data_scope") // 数据范围
  personality   String?                         // 特长/画像（由岗位池 trait 带出）
  createdAt     DateTime @default(now()) @map("created_at")
  updatedAt     DateTime @updatedAt @map("updated_at")

  @@index([orgType, orgId])
}
```

**设计说明**

| 决策 | 理由 |
|------|------|
| 一张表承载三层而非三张 | 避免 `ProviderTeamMember` / `AgentStaff` / `ConsoleStaff` 三套 CRUD |
| `dataScope` 沿用 lowercase 字符串而非新枚举 | DB 现有 `ProviderTeamMember.dataScope` 已是 `self`；且它与 `DataScopeInterceptor` 是**两套作用域**（平台级 vs 组织内级），不复用避免语义混淆 |
| `staffRole` 为 `String` 而非外键 | 支持自填自定义岗位（冲突 2 决定） |
| 不新增 `Role` 模型 | 岗位池是常量 + 自填，P2 再评估是否落 `StaffRole` 表 |

### 4.2 存量迁移

```js
// 一次性脚本（P0 已执行，迁移脚本 migrate-team-to-org-staff.mjs 已于 P2 删除）：
// ProviderTeamMember → OrgStaff（orgType=PROVIDER）
// P2 已清理：ProviderTeamMember 模型删除、表已 db push 落库删除，不再保留旧表
for (const m of await prisma.providerTeamMember.findMany()) {
  await prisma.orgStaff.upsert({
    where: { memberNo: m.memberNo },
    update: {},
    create: {
      orgType: 'PROVIDER', orgId: m.providerId, memberNo: m.memberNo,
      name: m.name, phone: m.phone, accountStatus: m.accountStatus,
      serviceType: m.serviceType, staffRole: m.teamRole,
      duties: m.duties, funcPerms: m.funcPerms, dataScope: m.dataScope,
      personality: m.personality,
    },
  });
}
```

**对外契约不变**：`/api/provider/team` 的请求/响应结构保持原样（字段名沿用 `teamRole` 别名），前端列表零感知。

## 5. 三层岗位池规范

### 5.1 服务商层（PROVIDER）

岗位池随「服务类型」联动，真值源为原型 `UI_Design/index.html:4691`：

| 服务类型 | 岗位池 | 职责池 |
|---|---|---|
| 特约设计 | 负责人 / 设计助理 / 客服专员 / 文案策划 | 内容策划、视觉设计、模板创作、客户沟通、订单管理、交付履约、售后处理 |
| 婚庆策划（别名词：婚礼策划） | 负责人 / 策划师 / 客服专员 / 执行督导 | 方案策划、流程设计、客户沟通、供应商统筹、现场执行、订单管理 |
| 摄影摄像 | 负责人 / 摄影师 / 后期师 / 客服专员 | 拍摄执行、后期制作、场景设计、客户沟通、作品交付、订单管理 |
| 花艺布置 | 负责人 / 花艺师 / 布置专员 / 客服专员 | 花艺设计、现场布置、物料统筹、客户沟通、验收维护、订单管理 |
| 司仪主持 | 负责人 / 司仪 / 礼仪顾问 / 客服专员 | 主持控场、流程彩排、台词创作、客户沟通、现场互动、订单管理 |
| 灯光音响 | 负责人 / 灯光师 / 音响师 / 客服专员 | 灯光设计、音响调试、设备管理、现场执行、客户沟通、订单管理 |
| 婚房布局 | 负责人/摆设布局/清扫整理/客服专员 | 新房布局、家具摆设、清扫整理、现场执行、订单管理 |
| 业务经理 | 负责人 / 执行专员 / 客服专员 | 客户沟通、订单管理、交付履约、售后处理 |

**通用追加岗位**（所有服务类型都可选）：店长/调度、财务专员。

> 原型每个服务类型还带 `trait`（特长画像），选中岗位后自动带入「特长」字段。

### 5.2 代理商层（AGENT）

| 岗位 | 默认职责 | 默认权限子集 | 默认数据范围 |
|---|---|---|---|
| 区域经理 | 辖区经营统筹、服务商拓展、业绩负责 | 辖区全量（按 `agent` 层域全集） | `agent` |
| 入驻审核员 | 服务商入驻资质审核 | `provider:review`、`provider:qualification` | `region` |
| 商务拓展 | 招商、服务商拜访、线索跟进 | `user:view`、`provider:review`（只读） | `region` |
| 财务专员 | 分润对账、提现发起 | `finance:view`、`finance:reconcile` | `agent` |
| 客服专员 | 工单处理、反馈跟进 | `feedback:handle`、`message:send` | `self` |

### 5.3 总台层（CONSOLE）

| 岗位 | 默认职责 | 默认权限子集 | 默认数据范围 |
|---|---|---|---|
| 超级管理员 | 全平台配置、角色与区域管理 | 10 域全集 | `all` |
| 内容运营 | 模板与公告运营 | `template:publish`、`template:review`、`announce:publish`、`announce:review` | `all` |
| 审核员 | 模板/资质/入驻审核 | `template:review`、`qualification:manage`、`provider:review` | `all` |
| 财务 | 提现审核、对账 | `finance:view`、`withdrawal:review`、`finance:reconcile` | `all` |
| 客服/工单 | 反馈处理、申诉仲裁 | `feedback:handle`、`appeal:arbitrate`、`message:send` | `self` |

### 5.4 数据范围取值（按层白名单）

| 层 | 可选值 | 默认 |
|---|---|---|

## 9. 权限边界红线

以下规则写入文档，P1 打通鉴权时**必须在服务端强制**。

| 编号 | 红线 | 说明 |
|---|---|---|
| R-01 | **员工权限 ≤ 雇主可用权限域** | 继承裁剪。不能给员工雇主自己都没有的权限 |
| R-02 | **财务发起 / 审批分离** | `withdrawal:review` 永不进执行岗权限池；员工最多发起，审批归老板/上级 |
| R-03 | **防自我提权** | `role:manage` / `team:manage` 仅老板/管理员持有，且不可转授 |
| R-04 | **执行岗数据隔离** | `dataScope=self` 的岗位只能看派给自己的数据；客户手机号用 `maskPhone` 脱敏（防离职带走客户） |
| R-05 | **离职即停用 + 留痕** | `accountStatus=DISABLED` 立即失效，动作写 `AuditLog` |
| R-06 | **停用必须真生效** | ⚠️ 依赖 P1 修复 `jwt.strategy.ts:12-52` 未校验 `status===DISABLED` 的漏洞；否则停用员工仍能登录，R-05 形同虚设 |
