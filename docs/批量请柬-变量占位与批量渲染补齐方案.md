## 1. 变量占位设计

### 1.1 两种表达方式的取舍

| 方案 | 机制 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A · 元素级整段替换 | 元素挂 `binding.key`，替换后 `el.text` = 名单值 | 样式整体继承、无排版歧义、实现面小 | 无法表达「尊敬的 X 先生」这类混合文案 | **默认方式** |
| B · 行内令牌 | 文本内写 `{{guest_name}}`，`applyTokens` 替换 | 支持前后缀混合文案、同段多变量 | 需防用户手输错 key；替换后长度变化影响排版 | **补充方式** |
| C · 富文本片段变量 | 变量带独立样式 | 表现力强 | 与当前 `TextElement` 单样式模型冲突，改造面大 | **不采纳** |

> **推荐**：**A + B 双轨并存，UI 统一收敛为一个「插入变量」动作**。
> 当元素文本为纯变量（整段等于 `{{key}}` 或用户从空元素插入）→ 走 A；当文本含前后缀 → 自动走 B。
> 判定规则复用现有实现：`current.includes('{{') ? applyTokens : resolveBindingValue`（`personalize.ts:102`）——**引擎已支持，本次只需让编辑器产出这种形态**。

### 1.2 命名规范

```
变量 key ::= 标准名单字段 key | ext_<自定义名>
             snake_case，小写字母 + 数字 + 下划线，首字符必须为字母
             正则：^[a-z][a-z0-9_]*$   （与 TOKEN_RE /^[a-zA-Z_][a-zA-Z0-9_]*$/ 兼容）
```

- **标准字段**：直接复用 `GUEST_FIELD_DEFS` 的 key，恒等映射零配置。当前 8 个：
  `guest_name`(姓名·必填) / `guest_title`(称谓) / `gender`(性别 M/F/U) / `unit`(单位) / `table_no`(桌号) / `phone`(手机号) / `address`(地址) / `remark`(备注)。
- **自定义字段**：必须 `ext_` 前缀，与标准字段在 UI 上分组展示，避免误当标准字段做校验。
- **「场次 / 日期」的归属（D1 已拍板）**：**只作模板自定义字段**，典型 key 为 `ext_session`（场次）、`ext_date`（日期）。
  - 不进 `GUEST_FIELD_DEFS` → 标准字段集维持 8 个、`GUEST_FIELDS_VERSION` 保持 `'1.0'`、CSV 下载模板列不变、存量名单零影响。
  - 使用路径：用户在「模板字段设计」页为模板新增自定义字段（写出 key 与中文表头）→ 名单按该 `columnDefs` 生成列 → 模板变量引用同一 key → 恒等命中。
  - 因自定义字段名由用户自拟，**体检环节必须存在**（见 §2.5），否则拼错 key 会静默生成空白请柬。
- key 一经使用即视为稳定标识：模板字段设计页改字段名时，**不重命名存量 key**（沿用既有「创建时快照、非实时绑定」的教训，见 MEMORY §11），只改 `label`。
- **D4 已拍板：变量 key 不强制等于名单字段 key**，允许模板用任意 key（尤其是 `ext_` 自定义变量），通过**显式映射**指向名单字段。因此变量下拉框列出「标准字段 key + 名单 `columnDefs` 的 key + 用户手输的新 `ext_` key」三类候选，用户可手输新 key 并建立映射（见 §2.1）。恒等（同名）自动匹配，无需映射。

### 1.3 可视化标记方式（三层，缺一不可）

| 层级 | 表现 | 目的 |
|---|---|---|
| 画布内 | 变量元素加 **2px 虚线描边**（品牌色 `#c81e42`）+ 右上角 `{{key}}` 胶囊徽章（12px，半透明底） | 一眼识别哪些是可替换位 |
| 图层面板 | 变量名后追加变量图标（`ICON_VARIABLE`，编辑器已有） | 定位深层/被遮挡元素 |
| 变量面板 | 独立「模板变量」列表：key · 中文名 · 命中元素数 · 样例值 · 跳转定位 | 集中管理与体检入口 |

**取舍**：画布描边**仅在「变量编辑模式」下显示**，不污染常态编辑与导出。理由：导出走 `personalizeSchema` 后的 schema，渲染层对 `binding` 零感知，不会误绘；但常态显示虚线会干扰视觉设计判断。提供一个顶栏开关（默认开启于「批量生成」上下文，如编辑器 `?batchList=` 进入时自动开启，沿用规范 §17.8）。

**重复占位管理**（你的第 4 问）：

- 变量面板按 key **聚合**，展示「命中 N 处」，点击即高亮并依次跳转全部命中元素（类似浏览器的查找结果导航）。
- 提供三个批量操作：**重命名 key** / **解除绑定（批量）** / **统一样例值**。
- **明确取舍**：**同一 key 的多处占位恒等替换，不支持「同 key 不同值」**。理由：名单是行级数据，同 key 不同值意味着同一行对同一字段有两个值，语义不成立；确有需求应新增自定义字段（如 `ext_session_2`）。

### 1.4 默认值预览（当前最大体验缺口）

现状：绑定后 `resolveBindingValue` 命中不到即返回 `''`，**设计态元素直接变空白**，用户无法判断排版是否被破坏。

**推荐**：扩展 `ElementBinding` 增加两个语义分离的字段——

| 字段 | 语义 | 使用时机 |
|---|---|---|
| `sample` | **设计态样例**（如 `guest_name` 样例「张三」、单位样例「新疆大学」） | 编辑器画布预览、模板选择弹窗预览、缩略图 |
| `fallback` | **运行态兜底**（名单该字段为空时填什么） | 批量渲染、导出 |

- 默认值自动取自 `GuestFieldDef.example`（`guest-fields.ts` 每个字段都有），用户可覆盖。自定义字段（`ext_*`）无 example，由用户在绑定时填写。
- 预览规则：**设计态永远显示 `sample`，绝不显示空白**。这让「绑定 → 看排版 → 调样式」的闭环成立。
- 运行态取值链（严格有序，**D4 后恢复映射层**）：
  ```
  srcKey = mapping?.[key] ?? key                       // 显式映射优先；未映射走恒等
  raw    = data[srcKey]                                 // 取名单字段值
  if (raw 非空) return String(raw)
  if (binding.fallback 非空) return binding.fallback     // 显式压过推断
  if (key === 'guest_title') return inferTitle(data)     // 性别推断（已实现）
  return ''                                             // → D2：整段变量元素隐藏
  ```
  > `mapping` 即 `BatchRenderProject.variableMapping`（`Record<templateKey, listFieldKey>`）；引擎 `resolveBindingValue(key, data, mapping?)` 已实现该取值链（T2 已落地）。

  > **顺序已定稿**：`fallback` **优先于** `inferTitle`。fallback 是用户显式填写的意图，inferTitle 只是「没填称谓时按性别猜」的默认行为，**显式压过推断**。
  > 多令牌混合文案按**各自 key** 取 respective fallback，不共用整段兜底（`applyTokens(text, data, mapping?, fallbacks?)`）。
  前两步已由 `resolveBindingValue` 实现（`personalize.ts:71`），本次补 `fallback` 一档 + 末端隐藏语义。
- **D2 已拍板：末端为空时隐藏元素**。作用域严格限定：
  - ✅ **整段变量元素**（有 `binding.key` 且 `text` 不含 `{{}}`）→ 替换结果为空串 → `visible: false`。
  - ❌ **混合文案元素**（`text` 含 `{{token}}`）→ 单个令牌为空则替换为空串、**保留前后缀、元素照常显示**。理由：这类元素是句子的一部分（如「尊敬的 {{guest_name}}」），整体隐藏会破坏句式与版式，不是用户想要的「隐藏对应元素」。
  - 隐藏采用既有铁律：`visible === false` 才隐藏（MEMORY §3），且只在 `personalizeSchema` 产出的**副本**上置位，模板本身不受影响。

## 2. 名单数据对接

### 2.1 变量 ↔ 名单字段：恒等 + 显式映射（D4 已拍板，恢复映射层）

变量 key 的取值来源分两级（引擎 `resolveBindingValue(key, data, mapping?)` 已按此实现）：

```
① 恒等（零配置主路径）：variableMapping 未配置该 key，且名单 columnDefs 含同名 key
        → srcKey = key，直接取 data[key]
② 显式映射：variableMapping[key] = <名单字段 key>
        → srcKey = mapping[key]，取 data[<名单字段 key>]
③ 兜底：data 取不到 → binding.fallback → inferTitle(仅 guest_title) → ''
```

- **恒等仍是默认与最常用路径**：模板变量 key 与名单字段 key 同名时，无需任何映射配置即可命中（标准 8 字段、`ext_` 自定义字段均如此）。
- **显式映射解决「两个不同名互指」**：模板用了 `ext_session`（自定义场次变量），但某份名单该列叫 `session_name` → 用户在映射 UI 里把 `ext_session → session_name` 一指即可，无需改模板、无需改名单。这是 D4 反转的核心收益——**一份模板可对接多份命名不同的名单**。
- 变量下拉框候选 = **标准字段 key 全集 + 名单 `columnDefs` 的 key + 用户手输的新 `ext_` key**。允许手输新 key（模板要表达名单里没有的纯展示变量，如固定文案变量），手输后必须建立映射或填兜底，否则体检拦截（§2.5）。
- `GuestMapping` 类型即本映射层的真值类型（`Record<templateKey, listFieldKey>`），本期**落库到 `BatchRenderProject.variableMapping`**（见 §2.1.1、§5.3）。

> 取舍备注：D1 让场次/日期走**模板自定义字段**，使「同模板换名单」时字段定义随模板走、天然同构；但「一份模板给多份异构名单」仍是真实需求，D4 反转通过显式映射层低成本覆盖，体检会在不匹配时明确拦截（§2.5），不会静默出错。

#### 2.1.1 映射持久化位（D4 恢复）

- `BatchRenderProject.variableMapping: Json` —— 存 `Record<templateKey, listFieldKey>`。项目级，编辑时落库（T4 / S3）。
- `RenderSnapshot.variableMapping: Json` —— 渲染时**快照**当前项目的映射，保证重渲（RERENDER / resume）取值稳定，不受后续映射编辑影响。
- 默认值 `{}`：空映射即「全恒等」，与旧行为向后兼容；存量项目未写该列 → 视为 `{}`。

### 2.2 字段校验

**直接复用** `normalizeAndValidateGuestData`（前后端双校验，规范 B15 已确立）：

- 归一化：trim、空串→`null`、`gender` 转大写、**丢弃未登记字段**（多余列不报错）。
- 校验：`required` / `maxLen` / `enum.values` / `pattern`（手机号 `^1[3-9]\d{9}$`）。
- **名单侧的校验与「变量是否匹配」是两件事**，不要混为一谈：前者校验值合法性，后者校验字段存在性。

### 2.4 缺失 / 空白值的兜底策略（分级，不一律留空）

| 级别 | 场景 | 策略（D2 已拍板） |
|---|---|---|
| L1 | 变量命中字段，但该行**值为空** | 用 `fallback`（无则空）→ **整段变量元素隐藏 `visible:false`**；混合文案元素保留前后缀、不隐藏 |
| L2 | `guest_title` 为空 | 自动走 `inferTitle`（性别推断先生/女士）✅ 已实现 |
| L3 | 变量 key 在名单**无同名字段**（`missing`） | 生成前体检拦截：核心字段阻断，选填字段警告 + 可现场填兜底值 |
| L4 | 名单字段未在模板中使用（多余字段） | 仅提示，不阻断（用户可能后续改模板） |

**兜底顺序**（引擎 `resolveBindingValue` 已落地，保持纯函数，含映射层）：

```
srcKey = mapping?.[key] ?? key                          // 显式映射优先，未映射走恒等
raw    = data[srcKey]                                   // 取名单字段值
if (raw 非空) return String(raw)
if (binding.fallback 非空) return binding.fallback      // 显式压过推断
if (key === 'guest_title') return inferTitle(data)      // 性别推断
return ''                                              // → L1：整段变量元素隐藏
```

> **注意 D2 的一个副作用**：若用户为 `guest_name` 之外的高频字段（如 `unit`）绑定了元素，而名单里大面积为空，会出现「请柬上大片元素消失」的观感。因此体检环节应**统计每行的空值命中数**并提示（如「有 12 行『单位』为空，这些请柬将不显示单位元素」），让用户提前知情并可补 `fallback`。

### 2.5 字段与变量不匹配时的提示方式

生成前**强制体检**（接线 `diffBindingKeys` + `GET /projects/:id/bindings`，二者都已存在但无消费方），弹出「变量匹配体检」对话框，三态分区展示：

| 分区 | 含义 | UI 表现 |
|---|---|---|
| ✅ 已匹配 | 模板变量 key 在名单 `columnDefs` 中存在 | 绿色，`{key} · {中文表头}` |
| ⚠️ 未匹配（选填） | 模板用了名单没有的变量（D1 自定义字段高发区） | 琥珀色：提示「该变量在名单中无同名字段」+ **填兜底值**输入框 + 「仍要生成」开关 |
| ⛔ 未匹配（核心） | `guest_name` 等关键变量无来源 | 红色，**阻断生成**，按钮禁用 + 说明「名单中缺少『姓名』字段，请检查名单所用模板」 |
| ⚠️ 空值预警（D2 副作用） | 字段存在但若干行值为空 | 琥珀色：`有 N 行『单位』为空 → 这些请柬将不显示该元素`，可就地补 `fallback` |
| ○ 未使用字段 | 名单有、模板没用 | 灰色折叠，仅提示 |

**取舍（D4 反转后）**：既然恢复映射层，不匹配时**可以现场改指向**——在体检对话框里把未匹配变量 `key` 映射到名单某个已有字段 key（写入 `variableMapping`）。改指向后该变量即转为「已匹配」，无需改模板、无需改名单。这是 D4 反转相对旧「强制恒等」方案的核心新增能力。

处置方式三选一（按推荐顺序）：
1. **改指向（映射）**：`ext_session → session_name`，零成本复用名单既有列；
2. **填兜底值**：所有行统一用该值，元素不隐藏；
3. **接受隐藏**：这些请柬不显示该元素（D2）。

仍**不做模糊匹配**——名单字段已支持「中文表头 → key」兜底（`normalizeGuestData` 里 `input?.[def.label]`），模糊匹配误匹配难解释；用户手动改指向时下拉列出名单所有候选 key，选择即确定。

## 3. 批量渲染流程

### 3.1 完整链路（现状 + 补齐项）

```
① 选模板        GET /projects  → 模板选择弹窗（已实现，含首页兜底缩略图）
② 建项目        POST /invitations/projects { templateId, listId }
③ 选人          POST /invitations/projects/:id/selection { listId, selectedRecordIds }
④ 【补】变量清单 GET  /invitations/projects/:id/bindings        ← 已存在，接线（含 mapping 视图）
⑤ 【补】体检     GET  /invitations/projects/:id/health  → 匹配/未匹配/空值预警  ← 新增（复用 diffBindingKeys）
⑥ 触发渲染      POST /invitations/batch-generate { projectId, mode?, targetRecordIds? }
                 └ 事务内：配额校验 → 建 RenderJob(PENDING) → 快照数据 → 异步 runJob
⑦ 渲染循环      runJob：深克隆模板 → personalizeSchema(逐条) → exportService.prepareSchema
                 → renderImage(带 90s 超时) → 写私有资产 → 逐条更新 progress/resultUrls
⑧ 进度反馈      前端轮询 GET /jobs/:id + /projects/:id/results（终态 SUCCESS|PARTIAL|FAILED 才停）
⑨ 分发          预览（带鉴权 Blob）/ 单张下载 / 打包 ZIP（子集）
```

**第 ⑦ 步的 `personalizeSchema(base, { id, data })` 必须保持「模板不被污染」**：它内部 `deepClone` 且返回新对象，逐条迭代安全。**不要把个性化后的 schema 写回模板**（模板保持单份真值，这是既有设计，不可破坏）。

### 3.2 进度反馈

- 现状：`RenderJob.progress / total` + `resultUrls`，前端 2s 轮询，终态以 **job 状态**为准（不以逐人 status 为准——免费赠样仅渲前 3 人，其余恒 `pending`，这条是既有防回归铁律）。
- **补齐建议**：`resultUrls` 增加逐条 `status/name/error`，让「任务进度表」能显示**已生成 / 失败 / 待生成**三态而不是只有成功条。现状表里已有此三态展示，只需后端补齐字段。

### 3.3 失败重试与断点续跑（现状缺口）

现状问题：重跑会**重渲全部 target**，已成功的重复消耗算力与时间（90s × N）。

**推荐做法**（按性价比排序）：

| 能力 | 方案 | 成本 |
|---|---|---|
| **断点续跑** | `POST /jobs/:id/resume`：读取该 job 的 `resultUrls`，把 `status==='ok'` 的 recordId 从 target 中剔除，仅重渲失败/缺失项。无需新表，复用 `resultUrls` | 低 ⭐ |
| **单条重试** | 复用现有 `mode:'RERENDER'` + `targetRecordIds:[recordId]`（规范 §18.6 已支持），前端在失败行加「重试」按钮 | 低 ⭐ |
| **整批重试** | 新建 job 重跑全量（现状行为），作为兜底保留 | 0 |
| **跨进程队列** | 现状是**进程内 worker pool**，服务重启即丢任务。若要真正可靠需 BullMQ/Redis 队列 + DB 兜底 | 高 |

> **推荐本期**：先做「断点续跑 + 单条重试」（低成本、覆盖 90% 场景），跨进程队列列为后续。理由：现有 `resultUrls` 已含逐条状态，断点续跑几乎零 schema 改动；而引入队列会牵动部署与监控，收益/成本比在 MVP 阶段不划算。
> **必须补的一处**：进程重启后遗留 `RUNNING` 状态的 job 需要**启动时回收**（扫 `status='RUNNING'` 且 `updatedAt` 超过 N 分钟 → 置 `FAILED` 并回退配额），否则额度会被占死（规范 E3 已明确此风险，现状缺这道闸门）。

### 3.4 生成作品的命名与归档

**保留现有规则**（已实现且合理，不轻易改）：

```
单文件：{seq}-{姓名}-{sha1(recordId).slice(0,8)}.png
        例：001-张三-3f2a9c11.png
目录：  private-assets/{users|orgs}/{ownerId}/invitations/{projectId}/{jobId}/
```

- `seq` 保序（与名单顺序一致，并发完成后按 `targetRecordIds` 顺序重排）✅ 已实现
- 姓名已 `replace(/[\\/:*?"<>|]/g,'_').slice(0,40)` 安全化 ✅ 已实现
- `sha1(recordId)` 后缀保证**同名客人不覆盖** ✅ 已实现

**补齐建议**：

1. **ZIP 内部结构**：`{模板名}_{YYYYMMDD}/001-张三-xxxx.png` + `manifest.json`。现状打包是平铺文件，超过 50 人时用户难以分辨来源。
2. **`manifest.json`**（新增，每 job 一份）：记录 `projectId / jobId / templateId / templateVersion / listId / mapping 快照 / 渲染时间 / 逐条 recordId→文件名`。用途：审计、复现、后续重渲对账。成本极低，价值高。⭐
3. 归档保留期：建议默认保留 90 天，到期清理任务化（见决策点 **D8**）。

## 4. 边界与风险

| 风险 | 现状 | 建议策略 | 级别 |
|---|---|---|---|
| **超长文本溢出** | 渲染层仅 `overflow:hidden`，长名会被硬裁 | 元素级 `binding.fit`：`'clip'`(默认裁剪) / `'shrink'`(自动缩字号至 `minFont`，再不够才裁) / `'wrap'`(换行，需行高支持)。**推荐默认 `shrink`，下限 60% 字号** | 高 |
| **特殊字符 / 换行** | 文件名已 sanitize ✅；文本因 `whiteSpace:'pre'` 会真换行 | ① 导入时把名单值内换行归一化为空格（名单字段语义上不该含换行）② emoji / RTL 字符在渲染前做**字体覆盖检查**（沿用 `buildFontFamilyStack` 的覆盖判定，缺字形时提示而非静默豆腐块） | 中 |
| **字体样式继承** | ✅ 天然继承：`personalizeElement` 只改 `text`，不动 `fontSize/fontFamily/color` | **保持不动，这是优点**。但需注意：替换后字号不变 → 长值溢出，与上一条联动处理 | 低（已正确） |
| **名单重复项** | 无去重逻辑 | 按 `recordId` 去重（**不用姓名**——同名不同人是正常场景）。提供「疑似重复」提示（姓名+单位+手机号三者全同）但**不阻断** | 中 |
| **大批量性能** | 单张 90s 超时、并发 4 | ① 单批建议上限 200 人，超出分批 ② 前置预估时长提示（人数 × 历史均值）③ 进度轮询降到 2s 且终态才停（已有）④ 免费档 3 人的小批量走同步快通道可选 | 高 |
| **并发限制** | `RENDER_CONCURRENCY=4` 硬编码，**无全局闸门** | ① 改配置化（env）② 增加**每人同时仅 1 个 RUNNING job** 的闸门（现状未校验，多标签页点两次会起两个 job 抢 puppeteer）③ 全局渲染信号量防单机打爆 | 高 |
| **配额与失败回退** | ✅ 失败条回退对应桶、RERENDER 不占配额 | 保持。新增：断点续跑时**不得重复扣减已成功条** | 已解决 |
| **模板改版后重渲** | ✅ C4 支持 RERENDER + targetRecordIds | 保持。**映射层（variableMapping）随项目持久化并快照进 RenderSnapshot**，重渲只需保证模板变量 key 未被重命名（key 稳定是硬约束，见 §1.2） | 已解决 |
| **PII 泄露** | ✅ 名单属 PII，AGENT 仅聚合计数，ADMIN 内容 404 | 保持。**新增的 manifest.json 含名单值快照，须同等级保护**，不得放公开桶 | 高 |

> **最高优先级的两条**：① **并发闸门**（多 job 抢 puppeteer 会导致大面积超时）② **RUNNING 僵尸 job 回收**（额度被占死且用户无法重试）。这两条都是现状真实存在的风险，建议与功能补齐同批做。

## 5. 数据结构（推荐，供前后端对齐）

### 5.1 变量绑定（元素上，扩展现结构）

```ts
// packages/core/src/schema.ts —— 扩展现有 ElementBinding（当前只有 key）
export interface ElementBinding {
  /** 稳定变量 key：标准名单字段 key 或 ext_ 前缀自定义名。正则 ^[a-z][a-z0-9_]*$ */
  key: string;
  /** 设计态样例值（编辑器/预览/缩略图用），默认取 GuestFieldDef.example */
  sample?: string;
  /** 运行态兜底值：名单该字段为空时使用 */
  fallback?: string;
  /** 溢出适配：默认 'shrink' */
  fit?: 'clip' | 'shrink' | 'wrap';
  /** shrink 模式的字号下限比例，默认 0.6 */
  minFontRatio?: number;
}
```

> 向后兼容：全字段可选，存量 `binding:{key}` 行为完全不变（`sample` 缺失时回落 `GuestFieldDef.example`）。

### 5.2 变量定义（设计态，**不新增表**）

```ts
// 由 collectBindingKeys(schema) 动态推导 + 元素上 binding 的附加属性聚合
export interface TemplateVariableView {
  key: string;                 // guest_name
  label: string;               // 姓名（来自 GuestFieldDef.label 或自定义名）
  isStandard: boolean;         // 是否标准名单字段（!key.startsWith('ext_')）
  elementIds: string[];        // 命中的元素（重复占位 → 多个）
  sample: string;              // 样例值
  fallback?: string;
  fit: 'clip' | 'shrink' | 'wrap';
}
```

> **取舍**：不建 `TemplateVariable` 表。理由：变量本质是「元素上的标注」，单独建表会与 schema 产生**双写不一致**（这正是既有教训——MEMORY §11「两套模板别混」）。单一真值源 = schema + `GuestFieldDef`。

### 5.3 映射关系 `VariableMapping`（D4 反转后恢复）

```ts
// packages/core/src/personalize.ts —— 既是运行态取值键，也是持久化结构
/** 模板变量 key → 名单字段 key 的显式映射；未列出的 key 走恒等（srcKey = key） */
export type VariableMapping = Record<string, string>;

// 持久化位：
//   BatchRenderProject.variableMapping: Json   // 项目级，编辑时落库
//   RenderSnapshot.variableMapping:  Json      // 渲染时快照，保证重渲稳定
```

- `resolveBindingValue(key, data, mapping?)` 取值链：`srcKey = mapping?.[key] ?? key` → `data[srcKey]`。
- 默认值 `{}` 即「全恒等」，与旧行为向后兼容；存量项目未写该列 → 视为 `{}`。
- 映射 UI（编辑器 / 体检对话框）只允许把 `key` 指向**名单 `columnDefs` 中存在的 key**，杜绝指向不存在的字段。

### 5.4 体检响应（生成前，含映射改指向）

```ts
export interface BindingHealth {
  projectId: string;
  templateId: string;
  listId: string;
  /** 已匹配：变量 key 在名单 columnDefs 中存在 */
  matched: { key: string; label: string }[];
  /** 模板用了、名单没有同名字段 —— 可现场改指向（mapping）或填兜底；核心字段阻断 */
  missing: { key: string; label: string; critical: boolean; remapTargets: string[] }[];
  /** 名单有、模板没用 */
  unusedFields: { key: string; label: string }[];
  /** D2 副作用预警：字段存在但若干行值为空 → 这些请柬将隐藏该元素 */
  emptyHits: { key: string; label: string; rows: number; fallback?: string }[];
  /** 生成是否被阻断（存在 critical missing 时 true） */
  blocked: boolean;
}
```

`critical` 判定：变量 key 为 `guest_name`（或名单侧 `required:true` 且模板依赖）→ 阻断；其余 → 警告 + 可现场填兜底值。
`emptyHits` 由服务端按选中子集逐行统计得出（前端拿不到全量行数据，必须在服务端算）。

### 5.5 渲染任务项（补齐逐条状态，供断点续跑）

```ts
// RenderJob.resultUrls 的元素结构扩展（现状已有 recordId/name/status/storageKey/error）
export interface RenderJobItem {
  recordId: string;
  name: string;                 // 名单 guest_name（展示用）
  file: string;                 // 0001-张三-3f2a9c11.png
  storageKey: string;           // 私有资产相对路径
  status: 'ok' | 'failed' | 'skipped';   // 新增 skipped = 断点续跑时跳过已成功项
  error?: string;
  renderedAt?: string;          // ISO，供 manifest 与保留期清理
}
```

### 5.6 端到端示例（一条记录的流转）

```jsonc

{ "id": "el_1", "type": "text", "text": "尊敬的 {{guest_name}} {{guest_title}}",
  "binding": { "key": "guest_name", "sample": "张三", "fallback": "贵宾", "fit": "shrink" } }
```

## 6. 关键取舍汇总

| # | 取舍 | 选择 | 理由 |
|---|---|---|---|
| 1 | 变量表达：元素级 vs 行内令牌 | **双轨并存** | 引擎已同时支持，UI 收敛为一个动作即可，成本极低 |
| 2 | 变量定义是否建表 | **不建表** | 避免与 schema 双写不一致（既有教训） |
| 3 | 画布标记是否常显 | **仅变量模式显示** | 不污染常态设计与导出 |
| 4 | 同 key 多处占位是否可不同值 | **不可** | 行级数据语义不成立，应新增自定义字段 |
| 5 | **映射层是否存在（D4）** | **存在，恒等 + 显式映射** | 一份模板可对接多份命名不同的名单；代价是新增 `variableMapping` 列 + 迁移 + 映射 UI，由体检支持现场改指向 |
| 6 | 是否做模糊自动匹配 | **不做** | 误匹配难解释；已有中文表头兜底；恒等契约下拼错就该被拦住 |
| 7 | 断点续跑 vs 跨进程队列 | **先做断点续跑** | 复用 `resultUrls`，零 schema 改动；队列留后续 |
| 8 | 超长文本默认策略 | **`shrink`（下限 60%）** | 裁剪丢信息、换行破坏版式，缩字号最安全 |
| 9 | 重复项是否阻断 | **不阻断，仅提示** | 同名不同人是正常场景，按 recordId 去重即可 |
| 10 | 是否保留现有命名/归档 | **保留，补 manifest** | 现有规则已正确，改动成本高且无收益 |
