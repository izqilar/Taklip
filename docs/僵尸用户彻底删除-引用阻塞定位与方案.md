# 回收站「僵尸用户 · 彻底删除」引用阻塞 —— 定位报告与方案设计

> 状态：**调研已完成，方案已于 2026-09-26 实施落地**（见文末「实施记录」）。本文件前 8 节为调研与方案设计，未改代码部分已验证。
> 调研时间：2026-09-26 ｜ 环境：dev 库 `h5design_platform`（55 个用户，其中僵尸 4 个）

---

## 0. 结论先行

1. **报错来自兜底，不是闸门**：`purgeZombieUser` 本身**没有任何业务留痕校验**，它直接调 `cascadeDeleteUserData` 物理删除，仅在数据库抛出外键约束 `P2003` 时才转成 409「该账号仍被其他业务数据引用」。所以提示语**说不出被谁引用**——它只知道有个外键挡住了。
2. **唯一的真实阻塞源是「合同」**：实测 4 个僵尸用户中 1 个被挡，命中的外键是 `ProviderContract_provider_id_fkey`（`onDelete=RESTRICT`）。`cascadeDeleteUserData` 的清理清单**漏掉了 `ProviderContract`、`TemplateOrder`、`User.agentId` 三处引用**，其中合同是必然命中项。
3. **被挡的那条合同早已作废**：`HT-2026-SP003` 的 `signStage = VOIDED`（negotiation 留痕：「总台：合同作废（降为普通用户 · 合同已作废）」），钱包四字段全 0、无订单、无提现。**它没有任何业务价值，纯粹是留痕记录未清理 + 校验不看状态导致的误挡。**
4. **僵尸判定与删除校验确实口径不一致，但方向是"入口太宽、出口太严"**：进回收站（`softDeleteUser`）**不做任何留痕校验**，所以带业务留痕的账号也能被丢进回收站；出口（purge）却用最严格的外键兜底拦死。僵尸用户并非系统自动判定（全库无自动标记逻辑），`isZombie` 100% 由运营手工软删除产生。
5. **提示文案对僵尸用户无意义**：僵尸用户 `status` 已是 `DISABLED`，提示"请改用禁用"等于让他做一个已经生效的操作，且**永远无法真正清除账号**。

**一句话定性**：不是脏数据，也不是僵尸判定过宽，而是 **①级联清理清单漏表 ②阻塞判定不区分记录的"有效/失效"状态 ③两个删除入口口径不一致** 三点叠加。推荐方案见 §5。

### 1.2 真正执行校验的地方

`cascadeDeleteUserData`（`admin.service.ts:539-579`）是唯一的"校验"，它的校验方式是**让数据库去撞外键**：

```ts
try { await this.prisma.$transaction(async (tx) => { /* 清理… */ await tx.user.delete(...) }); }
catch (e) { if (e?.code === 'P2003') throw new ConflictException('该账号仍被其他业务数据引用，无法删除；请改用「禁用」'); }
```

### 1.3 数据库实际外键（`information_schema` 实测，指向 `User` 的 22 条约束）

| 表.列 | onDelete | purge 前是否已清理 |

| `Ticket.reporter_id` | **RESTRICT** | ✅ 已 deleteMany |
| `Ticket.target_id / assignee_id` | SET NULL | ✅ |
| `Template.authorId` | SET NULL | ✅ 已 deleteMany |

### 1.4 与「服务商管理 · 删除」的口径差异

`deleteProviderAccount`（`admin.service.ts:452-532`）**有**业务留痕闸门，检查 6 类：订单（买/卖）、合同、提现、钱包流水、钱包余额、名下下级；命中即 409 且**带明细**（`该账号存在业务留痕（合同 1 份、…）`）。
`purgeZombieUser` **没有**这套闸门 —— 同一个 `cascadeDeleteUserData` 被两个口径完全不同的入口复用，是设计上的错配。

## 2. 矛盾根因分析（逐条排除你的三个假设）

| 假设 | 结论 | 依据 |
|---|---|---|
| ① 历史脏数据 / 软删记录未清理 | **部分成立，但性质是"合法留痕"而非脏数据** | `HT-2026-SP003` 是终审通过时连带创建的 `type=MAIN` 主合同（`apps/server/src/console/provider-console.controller.ts:2007+` 作废端点置 `VOIDED`），属**有意保留的业务凭证**，不是脏数据。问题在于**作废后没有相应清理/豁免路径**。 |
| ② 校验把已失效记录计入 | **成立，且是本次主因** | 外键 `RESTRICT` 与 `count()` 判定**都不看 `signStage`**：`VOIDED / EXPIRED / TERMINATED` 与 `EFFECTIVE` 被同等对待。该账号钱包全 0、无订单、无提现，唯一"资产"是一份已作废合同。 |
| ③ 僵尸判定条件过宽 | **不成立（无自动判定）+ 等效成立（入口无闸门）** | 全库 grep 无任何自动标记 `isZombie` 的逻辑，僵尸=运营手工软删除。`softDeleteUser`（`:586-632`）只校验 `isZombie/role/自身`，**不带任何留痕闸门** → 带合同的账号照样能进回收站，等效于"判定过宽"。 |

**补充发现（两个次要不一致）**
- `signStage` 的实际取值 `VOIDED` **未写进 schema 注释**（`schema.prisma` 注释列的是 `NEGOTIATING|AWAIT_PROVIDER_SIGN|AWAIT_SENIOR_SIGN|APPROVING|EFFECTIVE|EXPIRED|TERMINATED`），导致后续所有闸门口径都漏掉了它。
- `User.agent_id` 是 `SET NULL`：**purge 不挡**，但会把下级账号的归属静默置空且无审计；而 `deleteProviderAccount` 却把"名下 N 个下级"列为硬阻塞。同一事实两套结论。

### 3.2 结构性影响（未来必然复现）

| 指标 | dev 库现状 | 含义 |
|---|---|---|
| 僵尸用户 | 4 / 55，被挡 1（**25%**） | 量级小，但**比例不低** |
| 持有订单的用户 | 6 人 / 15 笔（`paid` 13、`refunded` 2） | 这 6 人一旦进回收站，**purge 100% 被挡**（TemplateOrder 未清理） |
| 持有合同的用户 | 3 人 / 4 份（`VOIDED` 1、`AWAIT_PROVIDER_SIGN` 2、`EFFECTIVE` 1） | 这 3 人一旦进回收站，**purge 100% 被挡** |
| 有下级的代理商 | 5 人 | purge 不挡但会静默置空归属（SET NULL），**数据静默变更风险** |

**结论**：按现有代码，`purge` 实际只对「注册后从未产生任何业务」的账号可用（恰好就是当前能删的那 3 个）。**任何有过交易、签约或管辖关系的账号，进了回收站就永远删不掉** —— 功能形同半残。

### 3.3 强行删除的风险分级

| 引用类型 | 业务价值 | 强删风险 |
|---|---|---|
| `EFFECTIVE / APPROVING / AWAIT_*` 合同 | **高**：法律凭证、抽成与保证金依据 | **严禁删除**（建议硬阻塞） |
| `paid` 订单 | **高**：资金流水、对账与开票依据 | **严禁删除** |
| 非零钱包 / 提现记录 | **极高**：资金追溯链 | **严禁删除** |
| `VOIDED / EXPIRED / TERMINATED` 合同 | **低**：已终结，仅存证意义 | 可删，**但须先归档快照**（合同号、阶段、协商留痕、时间戳写进 `AuditLog`） |
| `refunded` 订单 | **低-中**：已退款，仍建议归档 | 可删（归档后） |
| 消息/已读/工单/评价/资产/作品/资质/优惠券/加入申请 | 低 | 现状已在删，保持 |

## 4. 可选方案对比

| 方案 | 做法 | 优点 | 缺点 | 评价 |
|---|---|---|---|---|
| **A. 统一两套判定口径** | 让 `purgeZombieUser` 复用 `deleteProviderAccount` 的 6 类闸门 | 口径一致、实现省事 | 只是把"删不掉"从出口搬到入口前端，Kaili **依然删不掉**；且僵尸用户已在回收站，无法回退 | ❌ 必要不充分 |
| **B. 校验忽略已失效记录** | 阻塞判定排除 `VOIDED/EXPIRED/TERMINATED` 合同、`refunded` 订单、全零钱包 | 直击本次根因，改动小、风险低 | 只解决合同/订单，仍需补 cascade 清单才能真删掉 | ✅ **必选** |
| **C. 强制删除 + 级联清理** | 给僵尸用户提供"强制清除"，补齐 `ProviderContract`/`TemplateOrder`/`agentId` 清理 | 运营要的效果：真能删干净 | 若不分状态一律强删，**会毁掉 EFFECTIVE 合同与 paid 订单的法律/资金追溯链**，不可逆 | ⚠️ **仅在 B 的状态分级 + 归档快照前提下采用** |
| **D. 保留禁用 + 提示明细** | 409 文案列出具体引用（合同号+状态、订单笔数+状态…） | 可诊断性大幅提升，零数据风险 | 不解决"想删删不掉"，运营诉求没被满足 | ✅ **必选（作为 B+C 的兜底与提示层）** |

## 5. 推荐方案：**状态分级闸门 + 归档式级联清理 + 明细化提示**

**= B + C（分级）+ D，另配 A 收敛入口。** 核心原则：**有资金/法律价值的留痕硬阻塞并说清楚；已终结的留痕先归档快照再清理。**

### 5.1 新增统一引用盘点函数（单一真值）

在 `admin.service.ts` 抽出 `collectUserFootprints(userId)`，返回结构化清单，被 `purgeZombieUser`、`deleteProviderAccount`、僵尸详情三处复用，彻底消灭两套管径：

```
硬阻塞（blockers[]）    : EFFECTIVE/APPROVING/AWAIT_* 合同、paid 订单、非零钱包、
                          提现记录(pending/paid)、活跃下级账号
可清理留痕（cleanable[]）: VOIDED/EXPIRED/TERMINATED 合同、refunded 订单、
                          全零钱包、提现 failed、消息/已读/工单/评价/资产/作品/资质/券/加入申请
```

### 5.2 purge 新流程

1. `purgeZombieUser` 先跑 `collectUserFootprints`；
2. `blockers` 非空 → **409 + 明细文案**：
   `该账号仍有生效业务留痕：合同 HT-2026-SP003（已生效）、成交订单 3 笔（已支付）、钱包余额 ¥120.00。不可彻底删除，请先作废合同 / 退款后再试，或保留在回收站。`
3. `blockers` 为空 → 事务内：先把 `cleanable` 中**有价值留痕（合同/订单）**序列化进 `AuditLog.before`（含合同号、阶段、协商留痕、金额、时间），再执行级联清理，最后删 user；
4. 清理补漏：`providerContract.deleteMany`、`templateOrder.deleteMany`（仅非 paid，paid 已在 blockers 拦掉）、`user.updateMany({ where:{agentId}, data:{agentId:null} })` 显式解绑并审计。

### 5.3 前端可诊断化

- 僵尸**详情接口** `getZombieUserById` 附 `footprints: { blockers, cleanable }`，详情页展示「留痕清单」面板；
- 列表行/详情页的「彻底删除」按钮：有 blockers 时置灰 + tooltip 显示摘要；无 blockers 时才可点；
- 驳回提示改用服务端明细文案（现状 `users.tsx:200` 已原样透传 `e.message`，无需改前端即可生效）。

### 5.4 入口收敛（A）

`softDeleteUser` 进回收站时同步 `collectUserFootprints`，把 blockers 快照存审计；列表页显示「需先处理 N 项留痕」标记，避免"什么都往回收站扔、扔进去又删不掉"。

## 8. 回归验证要点

1. **Kaili（18199136644，VOIDED 合同）**：改后应**删除成功**；`AuditLog` 中 `USER_PURGE.before` 含合同 `HT-2026-SP003` 完整快照（阶段/协商/时间）。
2. **其余 3 个僵尸用户**：行为不变，仍删除成功（无回归）。
3. **持有 `EFFECTIVE` 合同的用户**：purge 必被 409 拒绝，**文案列出合同号与阶段,并提供业务处理的入口**。
4. **持有 `paid` 订单的用户**：purge 必被 409 拒绝；`refunded` 订单持有者可删且订单已归档。
5. **事务原子性**：人为制造 P2003（如临时插入一条 EFFECTIVE 合同）→ 必须整体回滚，`user` 行仍在，**无半删除脏状态**。
6. **外键兜底仍在**：cascade 之后若仍有未清理引用，仍报 409（不得静默吞掉）。
7. **审计链完整**：`USER_PURGE` / `PROVIDER_DELETE` 记录 before/after，强制清理的合同/订单可回溯。
8. **权限不变**：仅 `ADMIN`；非自身；ADMIN 账号不可删。

### 9.2 验证结果（全绿）
- **API 端到端**：①合成 VOIDED 合同僵尸 `purge` → 200 + 用户行物理删除 + 审计 `before.cleanableFootprints` 含该合同；②合成 EFFECTIVE 合同僵尸 `purge` → 409 + `messageKey:'pages.purge.blocked'` + `blockers` 含生效合同 + 用户未删（无半删除脏状态）；③3 个真实僵尸 `footprints.blockers` 全空（无回归）。
- **浏览器**：生效合同僵尸详情「留痕清单」渲染 + 列本地化明细 + 按钮禁用；干净僵尸显示「可安全彻底删除」+ 按钮可用；控制台 0 报错。
- 三端 typecheck 全绿；服务端 `build:compiled` 后由看门狗重启生效。

### 9.3 决策落地说明
- 决策①生效态口径以 `signStage` 字符串判定：`EFFECTIVE` = 硬阻塞；`VOIDED/EXPIRED/TERMINATED/NEGOTIATING/AWAIT_*/APPROVING` = 失效态可清理。订单以 `status`：`paid` = 硬阻塞，`refunded` = 可清理。
- 决策② EFFECTIVE 合同持有者 `purge` 必被 409 拒绝，仅可保留在回收站（其 `status` 已是 `DISABLED`，"改用禁用"提示无意义，故文案改为"保留在回收站"）。
- 决策③：存量 4 僵尸中 `18199136644`(Kaili) 在验证中被实际 purge（治理生效，证明 VOIDED 合同不再误挡）；其余 3 个非破坏性核查确认可删，保留。
- 决策④：409 明细文案服务端回带结构化 `blockers`，前端按 6 语言 `pages.purge.block.<kind>` 组合，不再硬编码中文。
