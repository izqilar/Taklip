## 为什么这个模型更合理（相对你原话的微调）

你的原话"运营端也像 web 端那样编辑模板作品"隐含了一个风险：**如果 web 和运营端编辑的是同一张 Template，就会出现双写冲突**——同一制品两处可改，"谁是最新"无法保证，同步 bug 和安全审计都难做。

我的建议把问题化解在**制品边界**上：

| 角色             | 编辑的制品                    | 能力                         | 后端落点                          |
| :--------------- | :---------------------------- | :--------------------------- | :-------------------------------- |
| Web 端（服务商） | **Project（个人草稿）**       | 自由创作、迭代，不对外       | `GET/PUT /api/projects`           |
| 运营端（服务商） | **Template（母版）** + 元数据 | 创作 + **唯一**发布/上下架权 | `GET/PUT /api/provider/templates` |
| 客户             | 只读                          | 选模板→克隆定制→发布页       | `useTemplate`                     |

要点：

1. **web 编辑不退化**：服务商在 web 端照常创作，存为个人 `Project` 草稿，体验与你现在完全一致。
2. **"要对外"才进闸门**：web 创作的产物通过"提交发布"动作（如 `POST /api/provider/templates/from-project`）生成/更新一条 `Template(status=PENDING, authorId=该服务商)`，再到运营端补全元数据并上架。这样 web 是"沙盒"，运营端是"发布闸门"。
3. **事实源唯一 = Template**：客户在 web 模板库看到的、被 `useTemplate` 克隆的，永远是运营端上架的 Template，与你上一轮拍板的"同一张表"完全一致。
4. **安全诉求闭合**：改变线上在售状态的发布/上下架收口在运营端，沿用现有 `subjectId/authorId` 作用域守卫，谁改自己的、何时改都有迹可查。

## 直接回答你的三个问题

**① web 端改设计，运营端能立刻更新吗？**
能，但前提是 **web 的修改必须写回 `Template.schema`，而不只是写个人 `Project` 草稿**。机制：画布以"编辑模板"模式打开该 Template → 改设计 → 保存 → 运营端读的是同一张 Template 表，自然立刻反映。若 web 画布只编辑个人 Project，则需一次"提交发布"把它同步成 Template，运营端才更新。

**② 已发布内容要做视觉优化，怎么办？**
已发布 = `Template.status=APPROVED`，正被客户 `useTemplate` 引用。正确做法是 **draft/live 分离**（见上图）：编辑时**不直接改线上在售的 schema**，而是保存为 draft 副本 → 预览确认 → 发布替换。这样修设计的同时不破坏线上、不影响存量客户。

**③ 修改操作逻辑（上图）**

1. 运营端「编辑」打开已发布 Template；
2. 画布加载其 `schema` 做设计修改；
3. **保存为 draft 副本**，不动线上 APPROVED 版本；
4. 预览确认；
5. 点「发布/替换」→ 新版本生效（建议保留旧版本便于回滚）。
