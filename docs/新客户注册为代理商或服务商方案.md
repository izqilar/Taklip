# 新客户注册为代理商 / 服务商 —— 完整方案

> 适用范围：基于当前 `apps/server`（NestJS + Prisma）+ `apps/admin`（运营端 :5174）+ `apps/web`（用户端 H5 :5173）现状。
> 前置改造已落地：`M1 关闭自服务捷径`、`M2 归属判定（regionPath + agentId）`、`M3 材料前置`、`M4 合同签约真实阶段与付费闸门`（见 `docs/服务商入驻与归属管线改造方案.md`）。本方案在其之上扩展**入口层**，不推翻既有铁律。

## 0 现状核实（代码事实，方案的地基）

| 项 | 现状 | 位置 |
|---|---|---|
| 工程构成 | `apps/` 下只有 `admin` / `server` / `web`，**无独立 APP / 小程序工程**；所谓"APP"即 web H5 移动端 | `apps/` |
| 注册接口 | `RegisterDto` 仅 `phone / password / nickname`；`register()` 只 create User，**role 默认 USER，不写 regionId / regionPath / agentId** | `auth.service.ts:60`、`dto/auth.dto.ts:3` |
| 注册页 | 无账户类型选择，注册成功即落 `/user/works` | `apps/web/src/pages/Register.tsx` |
| 入驻接口 | `POST /api/user/qualifications` 创建 `QualificationApplication`（kind: provider \| agent），已支持**材料随申请提交**、代理商辖区必填、服务商服务类型必选、**同 kind 在途申请去重** | `user-console.controller.ts:1094~1155` |
| 入驻入口 | `apps/web/src/user/Apply.tsx`，挂在 `ProtectedRoute` 下 → **必须先注册登录才能申请** | `apps/web/src/App.tsx:85~105` |
| 审批链 | 代理一审 `PATCH /api/agent/qualifications/:id/review`（FIRST_PENDING→FIRST_PASSED/REJECTED，`note` 只写入 `auditLog`）；总台终审 `POST /api/user/qualifications/:id/review`（`@Roles('ADMIN')`，body 仅 `{pass, final}`） | `agent-console.controller.ts:570`、`user-console.controller.ts:1352` |
| 终审落地 | provider→`role=SERVICE_PROVIDER` + `providerStatus=APPROVED` + serviceRoles + **regionPath + agentId** + 钱包 upsert + 自动生成主合同；agent→`role=AGENT` + 辖区（前置辖区唯一性拦截） | `user-console.controller.ts:1398~` |
| 落点 | `ROLE_HOME`：USER→web `/user/works`；SP→admin `/sp/studio`；AGENT→admin `/agent/dashboard` | `auth.service.ts:31` |
| 已有通知能力 | JOIN 隧道有结果通知（`Message scope=USER`）；**入驻管线没有任何结果通知** | `staff.service.ts:580` |

### 0.1 本轮核实新发现的 4 个缺口（方案需一并解决）

1. **总台终审不接收 `note`** → 驳回原因无处落库（`QualificationApplication` 也没有 `reviewNote` 字段），用户看不到驳回理由。
2. **入驻审核无任何结果通知**：无论一审通过、终审通过还是驳回，申请人都没有站内回执（只有"初审通过"会出现在消息列表里，那是 `user-console:899` 的通知聚合，非审核回执）。
3. **撤回是物理删除**：`DELETE /api/user/qualifications/:id` 直接 `prisma.delete`（`user-console.controller.ts:1326`），审计留痕丢失；与 JOIN 隧道的 `WITHDRAWN` 软删除语义不一致，也导致"驳回后重提"缺乏历史。
4. **入驻无主体唯一性校验**：`certNo`（统一社会信用代码 / 身份证）无唯一约束，同一主体换手机号即可重复入驻（手机号唯一挡不住）。
5. **代理商入驻提交时不做辖区重叠预检**：重叠只在终审前拦截（M2），用户填错辖区要等到终审才被拒，体验与返工成本高。

## 1 注册入口改造范围与推荐方案

### 1.1 三个候选

| 方案 | 做法 | 评价 |
|---|---|---|
| **A. 扩展现有注册流程**（推荐） | 注册页新增"账户类型"选择（普通用户 / 服务商 / 代理商），选定后展开对应资料段；注册仍只建 `USER`，随后用已登录态提交既有入驻申请 | 单一真源、复用全部既有校验与审计、手机号天然唯一 |
| B. 新增独立入驻入口 | 单独 `/settle` 通道，独立表单与接口、独立申请实体 | 与 `QualificationApplication` 双轨，去重/辖区/审计要重写两遍，易再次出现"绕过审批"的旁路（M1 刚修掉的正是这种） |
| C. 仅保留登录后申请（现状） | 不动注册页，靠 `/user/apply` | 新客户不知道要去哪申请，转化漏斗断在第一步，不符合诉求 |

### 1.2 推荐：**A（扩展注册流程）** + 保留 `/user/apply` 作为补充入口

**理由**
1. **守住 M1 铁律**：注册只建 `USER`，角色变更**只能**在总台终审 `APPROVED` 落地；账户类型在本方案中只是"入驻意图 + 资料前置"，绝不直接写 `role`。
2. **手机号唯一（`@unique`）天然防重复注册**；独立入口若允许多通道建户，反而出现一主体多账户。
3. **零重复建设**：去重、辖区校验、材料校验、审计、合同、归属全部复用既有管线。
4. `/user/apply` 继续服务"已注册老用户升级 / 驳回后重提"，与注册页共用同一后端接口。

**两段式提交（关键设计）**
- 第一段：`POST /api/auth/register`（无鉴权）**只扩展轻量可选字段**（`intent?: 'provider'|'agent'`、可选 `nickname/realName/regionId`），**不承载证件与附件**——避免未鉴权接口被刷资质数据。
- 第二段：注册成功拿到 token → 前端自动进入 `/onboarding` 资料页 → 调**既有受保护接口** `POST /api/user/qualifications` 提交完整材料（含附件）。未立即填写也可跳过，账户已是 `USER`，后续从 `/user/apply` 补提。

> 注册接口是否需要短信验证码见 §7 待确认项 2（当前无验证码能力，需评估是否本期引入）。

## 2 完整流程

### 2.1 流程总览（服务商 / 代理商共用骨架，分支见 2.3）

| # | 阶段 | 责任方 | 关键动作 | 状态 |
|---|---|---|---|---|
| 0 | 注册建户 | 新客户 | 选账户类型 → 手机号+密码注册 | 成为 `USER`（无资质） |
| 1 | 资料提交 | 申请人 | 填身份/资质/辖区 + 上传附件 → 提交入驻申请 | `FIRST_PENDING` |
| 2 | 代理商一审 | 辖区 AGENT | 辖区匹配、材料完整性、红线初筛、重叠预检 | `FIRST_PASSED` / `REJECTED` |
| 3 | 总台终审 | ADMIN | 风险预检（重复主体/黑名单/造假）+ 人工裁定 | `APPROVED` / `REJECTED` |
| 4 | 合同签约 | 平台 ↔ 服务商 | 系统自动生成主合同 → 线上签 → 生效 | `EFFECTIVE`（M4 已实现） |
| 5 | 开展业务 | — | 身份+资质+合同三闸门齐备 | — |

### 2.2 必填资料（按账户类型分支）

**共性（provider / agent 都要）**
- 注册：手机号（唯一）、密码（≥6）、昵称（可选）
- 申请：申请人姓名 `applicantName`、联系手机 `phone`、申请理由 `reason`
- 资质：证件类型 `certType`、证件号 `certNo`、有效期 `certExpire`（或长期 `certLongTerm`）、发证机关 `issuer`、附件 `attachments[]`

**服务商（provider）额外**
- 服务类型 `serviceScopes`：DESIGN / PHOTO / VENUE / FLORAL / STEWARD / PERFORM，**至少一项**（后端已强制）
- 开展服务区域 `regionPath`：选填（缺省由归属推导；**建议本期改为必填**——它决定"归哪个代理商管"，留空会产出孤立主体）

**代理商（agent）额外**
- 代理辖区 `regionPath`：**必填且须三级完整**（省/市/区）（后端已强制非空，建议补"必须到区县级"校验）
- 辖区不与既有代理商重叠：提交时**预检**（新增，§0.1-5）

### 2.3 审核状态流转

```
(提交) FIRST_PENDING
   │ 代理商一审 PATCH /api/agent/qualifications/:id/review
   ├─ 通过 → FIRST_PASSED（可补填材料 → FINAL_PENDING）
   └─ 驳回 → REJECTED（附 reviewNote，可修改后重提）
FIRST_PASSED ──补填材料── FINAL_PENDING
   │ 总台终审 POST /api/user/qualifications/:id/review?final
   ├─ 通过 → APPROVED → applyQualificationResult（身份/资质/辖区/agentId/钱包/合同）
   └─ 驳回 → REJECTED（附 reviewNote）
任意在途（FIRST_PENDING / FIRST_PASSED）→ 申请人可撤回
```

> 注：M3 后材料已可随申请提交，因此"提交即可 `FINAL_PENDING`"与"一审后补填"两条路并存，状态机不变。

### 2.4 审核通过前后的权限差异

| 能力 | 通过前（`USER`） | 服务商通过后 | 代理商通过后 |
|---|---|---|---|
| 登录落点 | web `/user/works` | admin `/sp/studio` | admin `/agent/dashboard` |
| 运营端工作台 | 不可进入 | 服务商工作台（发作品/模板/服务） | 代理商工作台（辖区一审/招商/合同只读） |
| 上架免费供给 | — | ✅ | — |
| 上架付费供给 | — | 需 MAIN 合同 `EFFECTIVE`（M4 闸门） | — |
| 钱包 / 提现 | — | 终审时自动建钱包；提现走代理一审+总台放行 | 无 |
| 辖区治理 | — | 被辖区代理商管辖（`agentId`） | 辖区内入驻/提现一审、合同查看（只读） |
| 发公告 | — | 仅一般消息 | 权威公告需总台审核 |
| 驳回后 | 保持 `USER`，可查看原因并重提 | — | — |

## 3 后端需要的改动

### 3.1 模型层（`schema.prisma`）

| 模型 | 改动 | 说明 |
|---|---|---|
| `QualificationApplication` | **新增** `reviewNote String?`、`firstReviewedById?/At?`、`finalReviewedById?/At?`、`resubmitOfId?`（重提溯源）、`materialSubmittedAt?` | 支撑驳回原因回填、审核人留痕、重提链路（现状全无） |
| `QualificationApplication` | 撤回改为 `WITHDRAWN` 软删除（**现状是物理 delete**） | 保留审计；与 JOIN 隧道语义统一 |
| `User` | **不新增角色/状态**；`regionId/regionPath/agentId/providerStatus` 已齐备 | 注册可选写入 `regionId`，身份仍只在终审落地 |
| （可选）`certNo` 唯一性 | 新增 `@@index([certNo])`，或独立 `SubjectUnique(certType,certNo)` 表做软校验 | 防换号重复入驻（§0.1-4），是否硬约束见 §7-8 |

### 3.2 接口层

| 接口 | 改动 | 优先级 |
|---|---|---|
| `POST /api/auth/register` | `RegisterDto` 增可选 `intent`、`realName`、`regionId`；`register()` 写入昵称/实名/区域；**不写 role、不建申请**；建议加限流 | P1 |
| `POST /api/user/qualifications` | ① 附件按 kind 强校验（provider/agent 各自必传清单）；② agent `regionPath` 校验到区县级；③ agent **提交时辖区重叠预检**（复用 `findRegionConflict`，重叠即阻断并给出冲突辖区）；④ 重复主体软校验（同 `certNo` 已 APPROVED 主体告警/拦截） | P0 |
| `POST /api/user/qualifications/:id/review` | body 增 `note`；落库 `reviewNote` + `finalReviewedById/At`；**新增结果通知**（通过/驳回） | P0 |
| `PATCH /api/agent/qualifications/:id/review` | `note` 除 `auditLog` 外同步写入 `reviewNote` + `firstReviewedById/At`；**新增结果通知** | P0 |
| `DELETE /api/user/qualifications/:id` | 物理删除 → `WITHDRAWN` 软删除，列表默认隐藏 | P1 |
| `GET /api/agent/qualifications` | 补 `kind` 过滤参数（现状 provider 与 agent 申请混列） | P1 |

### 3.3 通知与审计

- 新增统一回执方法（对齐 `staff.service.notifyJoinResult`）：写 `Message{ type:'NOTICE', scope:'USER', recipientId: 申请人, title/content }`，覆盖"一审通过（请补充资料）/ 一审驳回（含原因）/ 终审通过 / 终审驳回（含原因）"。
- 审核动作全部落 `auditLog`（一审已有 `AGENT_QUALIFICATION_FIRST_REVIEW`，终审建议新增 `ADMIN_QUALIFICATION_FINAL_REVIEW`）。

### 3.4 与既有管线的衔接点（必须对齐，防回归）

| 衔接点 | 位置 | 要求 |
|---|---|---|
| 归属判定 | `applyQualificationResult` / `resolveAgentId`（M2） | 服务商终审时写 `regionPath` + 最长前缀 `agentId`；无辖区覆盖留空不阻断 |
| 辖区唯一性 | `findRegionConflict`（M2） | 代理商终审前强校验；本方案再前移到**提交时预检** |
| 合同闸门 | `ensureProviderContract` + `advance`（M4） | 服务商终审 `APPROVED` 自动出草稿；付费上架需 `EFFECTIVE` |
| 落点 | `ROLE_HOME`（auth.service:31） | 不改，身份落地后自动切工作台 |
| 待办角标 | `console/badges` → `onboarding` | 建议细分"待一审 / 待终审"两档 |
| 扩展业务 | `pendingServiceRoles` | 已入驻服务商扩业务走既有管线，不占用新注册流程 |
| 招商转化 | `RecruitLead`（stage=WON） | P2：意向转入驻时预填申请（邀请码），见 §7-1 |

## 5 关键风险与边界情况

| # | 风险 / 边界 | 现状问题 | 对策 |
|---|---|---|---|
| 1 | **普通用户升级为服务商** | 老用户走 `/user/apply`；注册新流程与之共用同一接口 | 同一时刻只允许一个在途申请（已有 dup 去重，REJECTED 不在去重范围内 → 可重提）；升级与注册只是入口不同，后端同源 |
| 2 | **重复注册 / 重复主体** | 手机号唯一挡不住换号重开；`certNo` 无约束 | 提交时按 `(certType, certNo)` 软校验命中已 APPROVED 主体 → 告警或拦截（先告警，避免误伤历史脏数据） |
| 3 | **资料缺失** | 前端校验可被绕过；一审若审空壳申请则闸口失效 | 后端按 kind 强校验附件必传清单，缺件直接 400，不进一审 |
| 4 | **驳回后重新提交** | 物理删除导致无历史；无重提次数限制 | 软删除保留历史 + `resubmitOfId` 溯源；可选冷却期（§7-5）；重提生成**新申请**，不就地复活旧单 |
| 5 | **代理商辖区重叠** | 只在终审前拦截，返工晚 | 提交时预检并即时提示冲突辖区；终审前再强校验（双保险） |
| 6 | **无辖区覆盖（孤立主体）** | 服务商 `regionPath` 选填/留空 → 不落入任何代理商 | 本期建议服务商区域改必填；留空时标记"待分配"并在总台待办提示 |
| 7 | **未鉴权注册接口被刷** | 注册无验证码、无限流语义 | 资质材料不放注册接口（两段式）；注册接口限流；是否上验证码见 §7-2 |
| 8 | **通知不可达** | 无短信/邮件通道 | 站内消息为准；**申请详情页必须能自查状态与驳回原因**，不依赖通知 |
| 9 | **存量兼容** | 已 APPROVED 主体、老 USER | 合同生成幂等（M4）；老用户走 `/user/apply`；存量 `agentId` 已回填（M2 脚本） |
| 10 | **越权** | 入驻申请创建走 `resolveUserId/resolveTarget` | 新入口必须复用同一套鉴权，禁止为"注册即入驻"新开免鉴权通道 |

## 7 待确认事项（需拍板后才进入实施）

1. **"APP" 的载体**：仓库无独立 APP/小程序工程，当前只有 `apps/web`（H5）。本方案按"web H5 注册页扩展"设计；未来开发原生/小程序端，将要共用同一后端接口（推荐共用）。
2. **注册将来要强制短信验证码**：当前注册仅手机号+密码，无验证码能力。将来要求风控，需新增短信通道与限流（成本独立评估）先做占位。
3. **实名联动**：入驻终审通过前严格要求进行实名认证,保持实名独立审核（现状 `UNVERIFIED/PENDING/APPROVED/REJECTED`）？
4. **代理商要签"代理协议"**：M4 只做了服务商主合同的自动生成；代理商与平台之间也需线上协议（影响合同闸门范围）。
5. **驳回重提限制**：设冷却期 / 最大重提次数（默认建议：不限制次数，仅保留历史与统计）。
6. **撤回改软删除**：接受 `WITHDRAWN` 语义变更（现状物理删除，改动会影响列表默认过滤）。
7. **服务商区域是改必填**：改必填可消灭孤立主体，但会增加一步表单填写（推荐改必填）。
8. **certNo 唯一性强校验**：先软校验告警 vs 直接拦截（历史脏数据可能误伤，建议先告警 + 人工判定）。
9. **招商意向转入驻**：是需要 `RecruitLead(stage=WON)` → 预填入驻申请（邀请码）的转化链路（本期可不做，P2）。

### 9.2 §7 待确认事项的最终决策

1. **APP 载体** → 按 web H5 实施；未来原生/小程序端**共用同一后端接口**（未新建工程，待产品排期）。
2. **短信验证码** → **本期不做**。注册接口不承载资质材料（两段式已降低被刷价值）；如需风控再引入短信通道与限流，成本独立评估。
3. **实名联动** → **终审 `APPROVED` 时同步置 `realNameStatus=APPROVED`** 并固化实名姓名；实名状态字段保留，供后续监管复查。
4. **代理商代理协议** → **已实现**：终审通过自动生成 `type=AGENCY` 区域代理协议（甲方恒为平台、区域独家），复用 `ProviderContract` 一表。
5. **驳回重提限制** → **不限制次数**，保留历史与 `resubmitOfId` 溯源；重提生成新申请，不就地复活旧单。
6. **撤回软删除** → **已改为 `WITHDRAWN`**，列表默认隐藏，与 JOIN 隧道语义一致。
7. **服务商区域必填** → **已改必填**，消灭无代理商管辖的孤立主体。
8. **`certNo` 唯一性** → **分级**：命中已入驻主体（`APPROVED`）拦截；仅命中在途申请时告警旗标，交人工终审判定（防历史脏数据误伤）。
9. **招商意向转入驻** → **不代客创建申请**，只置 `WON` 并产出带手机号预填的入驻邀请链接，由意向主体本人完成注册与资料提交。

### 9.3 刻意未做（含理由）

- **自动审批**：预检只标记、不自动放行。自动误批会让不良主体立即开展业务并收取消费者定金，损失不可逆；裁定权始终在人工（M5 设计取舍）。
- **`regionPath` DB 唯一约束**：同辖区需被多个服务商共用，硬约束会误伤；改为应用层双向前缀冲突检测（提交时预检 + 终审前强校验）。
- **合同可靠电子签（CA/时间戳/哈希）**：当前只实现状态机与付费闸门；具备法律效力的电签需接入第三方合规服务，作为独立专项。
- **短信/邮件通知通道**：站内消息为准，申请详情页可自查状态与驳回原因，不依赖通知可达。
