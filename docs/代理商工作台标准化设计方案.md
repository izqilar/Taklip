## 0. 背景与定位

服务商（SP）是平台业务的**核心载体**，其业务从终端用户 → 代理商 → 管理总台贯穿全链路。代理商（AGENT）因此天然是**辖区治理中枢**：辖区内 SP 与 USER 的每一项业务动作，都应在代理商工作台里对应成一个可处理的工作项（审核 / 复核 / 跟踪 / 结算 / 处理）。

**v2 新增核心定位 —— 内容审核闸口（辖区第一线）**：SP 对外发布的一切内容（**模板上架 + 服务/作品上架**）在可被终端用户看到/购买之前，**必须经过所属代理商的审核闸口**；代理商尤其要严把**法律与意识形态红线**。这是代理商区别于总台/服务商的核心治理职能。

当前代理商视角的菜单（`resources.tsx` 246–301 行）仅 **11 项**，且除 `teamsetting` 外大部分业务项**未分组**；而静态原型 `MENU.agent` 已规范了 **7 组 20 项** 的完整结构。本方案以「用户 / 服务商菜单为基准 + 业务管线逻辑」双约束，对代理商工作台做**标准化重排 + 查漏补缺**，并明确内容页缺口与复用策略。

### 设计原则
1. **镜像 SP / USER 结构** —— 代理商监督辖区内 SP/USER 活动，菜单分组与命名尽量与二者对齐，降低认知成本。
2. **覆盖全管线** —— SP/USER 在辖区内的每个业务动作都必须落到代理商的一个工作项。
3. **代理商专有职能** —— 招商拓客、自身佣金结算、辖区业务参数配置、**内容审核闸口（红线把关）**。
4. **分组标准化** —— 沿用 SP 的 7 组范式 + 数据看板；命名与 SP/USER 一致。
5. **角标纪律** —— 每个角标 = 真实后端统计的「待处理子集」，绝不统计全表。
6. **视角铁律（P0）** —— AGENT 登录后 `view==='agent'===自身角色===自身工作台`，直接展示自身数据，**绝不强制选 subject**；仅 ADMIN 视察 AGENT 才经 `?subject=`（带辖区校验）。
7. **红线一票否决（新增）** —— 内容审核以「法律/意识形态红线」为最高优先级，机审+人审双保险，审核留痕可审计。

**问题诊断**：
- 业务项**全堆在根层、未分组**，既不符合 SP/USER 已定型的「分组范式」，也无视原型 `MENU.agent` 的 7 组设计。
- **管线关键工作项缺失**：入驻审批、资质审核、合同管理、内容审核（模板/服务）、意见反馈、提现初审、通知公告、招商申请、意向池、业务设置 共 **11 项** 在代理商视角完全没有入口。
- `agent/wallet` 命名「结算与钱包」易与服务商的「我的钱包」混淆；原型中代理商财务只有「结算总览」。

### 1.1 现状 · 内容审核闸口（v2 重点 · 代码核对事实）
经核对 `apps/server` 后端，当前内容发布与审核的真实状态如下（**非推测**）：

| 内容类型 | 后端模型 | 提交/发布端点 | 当前闸口 | 代理商权限 | 红线把关 |
|---|---|---|---|---|---|
| **模板** | `Template`（`prisma`） | `POST /api/templates` → `PENDING` | 有 `PENDING`，人工审核 `PATCH /api/templates/:id/review` | **仅 `@Roles('ADMIN')`，代理商无权** | 仅 `ContentSafetyService` 关键词机审（硬编码词库、命中即自动驳回、无人工红线复核） |
| **服务/作品** | `Project`（`prisma`） | `POST /api/provider/services/:id/publish` → **直接 `published`** | **无任何待审态、无审核闸口** | 无 | 无（发布即公开可见/可购买） |

**结论**：
- 模板线「有闸口但闸口在总台、不在代理商」——与用户要求的「代理商严把红线」相悖。
- 服务/作品线「连闸口都没有」——SP 一发即公开。这是红线风险敞口最大的地方。
- 现有 `ContentSafetyService` 是**机审占位**：词库硬编码不可运营配置、图片审核 `return {passed:true}` 为空实现、审核不记录"谁为红线负责"。
- 因此 v1 方案"复用 `templates.tsx` 切 AGENT 辖区"在当前后端**无法落地**（代理商无审核接口权限），必须配套后端改造。

## 2. 标准化目标菜单树（8 组 · 21 项）

> 分组键沿用 `MenuGroupKey`，新增 `providersupervise`(辖区服务商) / `regionops`(辖区运营) / `recruit`(招商拓展) / `contentreview`(内容审核)；
> `databoard` / `finance` / `message` / `teamsetting` 已存在。
>
> **「内容审核」独立成组**（v2）：它既是代理商区别于总台/服务商/用户的核心治理职能，又是用户本次特别强调的红线把关入口，不应淹没在「辖区服务商」里。

### 分组顺序（`GROUP_ORDER` 增量调整）
在全局 `GROUP_ORDER` 中把代理商专用组按以下相对顺序插入（其余组不受影响，因它们不出现在代理商视角）：
`databoard → providersupervise → contentreview → regionops → recruit → finance → message → teamsetting`

新增分组标签（`GROUP_LABEL`）：
- `providersupervise: '辖区服务商'`
- `contentreview: '内容审核'`
- `regionops: '辖区运营'`
- `recruit: '招商拓展'`

## 3. 业务管线映射（为什么每项必须存在）

### 3.1 服务商（SP）↔ 代理商（AGENT）
| SP 侧菜单（已定型） | 业务动作 | 代理商对应工作项 | 后端端点推断 / 现状 |
|---|---|---|---|
| 业务申请 `sp/apply`（入驻/业务新增/升级） | 提交 → 初审 → 终审 → 签约 | **入驻审批** `agent/apply` + **合同管理** `agent/contract` | `admin/provider-review`（AGENT 辖区，过滤入驻/升级） |
| 资质管理 `sp/qualification` | 证照审核（初审/复审） | **资质审核** `agent/qualification` | `qualificationReview` 或 `provider-review`(资质) |
| 合同管理 `sp/contract` | 与代理/总台在线签约 | **合同管理** `agent/contract` | `agent/contract` 或 `provider/contract` |
| 模板管理 `sp/templates`（上架） | 上架审核（**红线把关**） | **模板审核** `agent/template-review` | 现状 `POST /api/templates`→PENDING，**审核仅 ADMIN**；v2 新增 `GET/PATCH /api/agent/templates` 辖区审核端点 |
| 服务管理 `sp/services`（上架） | 上架审核（**红线把关**） | **服务审核** `agent/service-review` | 现状 `publish`→直接 `published`、**无闸口**；v2 新增 Project 待审态 + 审核端点 |
| 我的订单 `sp/orders` | 履约跟踪 | **辖区订单** `agent/orders` | `agent/orders` |
| 意见反馈 `sp/complaints` | 投诉/建议/升级 | **意见反馈** `agent/complaints` | `admin/feedback`(投诉过滤) |
| 我的评价 `sp/feedback` | 辖区协商/超时升级总台 | **服务评价** `agent/feedback` | `admin/feedback`(AGENT 辖区) |
| 提现管理 `sp/withdraw` | 提现初审 → 总台终审 | **提现初审** `agent/withdraw-review` | `admin/withdrawals`(AGENT 辖区) |
| 收入明细 `sp/income` / 我的钱包 `sp/wallet` | 辖区内抽成分账 | **结算总览** `agent/settle` | `agent/wallet`（结算明细） |

### 3.2 用户（USER）↔ 代理商（AGENT）
| USER 侧菜单（已定型） | 业务动作 | 代理商对应工作项 | 后端端点推断 |
|---|---|---|---|
| 我的订单 `user/orders` | 履约监督 | **辖区订单** `agent/orders` | `agent/orders` |
| 我的反馈 `user/complaints` | 投诉/建议 → 升级总台 | **意见反馈** `agent/complaints` | `admin/feedback` |
| 通知公告 `user/notices` | 平台公告辖区转发 | **通知公告** `agent/notices` | `notices`(AGENT 辖区) |
| 业务消息 `user/messages` | 待办处理 | **业务消息** `agent/messages` | `messages`(AGENT 辖区) |

### 3.3 代理商专有（不镜像 SP/USER）
- **内容审核（模板审核/服务审核）**：SP 对外内容的辖区第一线闸口，红线把关（v2 核心，见第 11 节）。
- **招商申请 / 意向池**：代理商主动拓客（区别于 SP 自驱动的「入驻审批」），原型 `MENU.agent` 独立成「招商拓展」组。
- **结算总览**：代理商自身佣金分账（其发薪由总台 `考核与分佣/结算管理` 执行，故不另设代理商自有钱包提现）。
- **业务设置**：辖区参数配置（辖区范围 / 审核开关 / 公告转发开关）。

## 11. 内容审核闸口专项设计（v2 核心 · 红线把关）

> 本节约等于对 v1 方案「服务监管」一项的**彻底重写与补足**。目标是把用户强调的「服务商上架必须经代理商内容审核闸口、尤其模板红线把关」落成可实施的管线。

### 11.1 两条管线（必须拆分的根因）
| 管线 | 对象模型 | 现状风险 | 改造要点 |
|---|---|---|---|
| **模板审核** `agent/template-review` | `Template`（已有 PENDING） | 闸口在总台（ADMIN 审），代理商无权 | 把一线审核权下沉到代理商（按 regionPath）；保留总台 oversight |
| **服务审核** `agent/service-review` | `Project`（当前发布即 `published`） | **无闸口**，SP 一发即公开/可购买 | **新增待审中间态**，发布闸口化 |

> 二者对象模型、风险面（模板含可复用的设计素材/文案，服务含履约承诺/价格/商家信息）不同，审核重点不同，**不能合并成一个"服务监管"**。

### 11.2 发布闸口机制（硬性约束）
- SP 提交/发布内容 → 进入**「待审」态**，**不对外可见、不可购买、不可被用户检索**。
- 仅当代理商审核通过（APPROVED/上架）→ 内容转为公开可用。
- 驳回 → 内容回到草稿/驳回态，SP 收到**整改意见（含红线类别）**，可修改后重新提交（重新进入待审）。
- 严重违规（触碰红线）→ 代理商可**「标记红线 / 立即下架」**并自动上报总台（ADMIN 接收预警）。

### 11.3 两级审核与权责（代理商 vs 总台）
- **代理商 = 一线辖区闸口**：按 `regionPath` 过滤，仅审本辖区 SP 内容，是日常红线把关主体。
- **总台（ADMIN）= 终审 + 抽检 + 违规下架 + 申诉终审 + 红线词库管理**：保留现有 `templates/admin` 等 oversight 能力，但对一线审核质量负巡查责任。
- **是否双重审批（代理审完再总台审）？** 方案建议**不双重审批**（避免效率与责任模糊），采用「**代理一审 + 总台抽检/终审/上诉**」模式。此点列为 §12 决策点 6，需用户拍板。

### 11.4 红线复核工作流（机审 → 人审）
1. **机审前置**：SP 提交时 `ContentSafetyService` 扫描（v2 需升级：词库 DB 可配置、接入图片机审、扫描结果结构化回传命中词/字段）。
2. **机审命中 → 转「待人工红线复核（疑似）」并高亮命中字段**，不自动驳回（避免误杀，且强制人工看一眼红线字段）。
3. **人工审核面板必须内置红线清单勾选**（政治/意识形态、色情、暴力、赌博、毒品、诈骗、侵权、虚假宣传、其他），审核员逐项确认"已核查无误"或"发现红线（选类别 + 描述违规点）"。
4. **审核动作三选一**：
   - **通过（合规）**：内容转公开；
   - **驳回（必须选红线类别 + 整改意见）**：回退，SP 可改后重提；
   - **标记红线下架（严重）**：立即下架并上报总台。
5. **复核/申诉**：被驳回/下架的内容，SP 可申诉 → 代理商复核 → 总台终审（复用并扩展现有 `TemplateAppeal` 机制到服务）。
6. **留痕审计**：每次审核记录 reviewer、时间、决定、红线类别、意见、命中词 → 写入审计（合规取证，应对监管检查）。

### 11.5 代理商工作台页面形态
- **模板审核台** `agent/template-review`：本辖区待审模板队列 + 模板预览（渲染） + 红线清单面板 + 审核动作 + 历史/审计。
- **服务审核台** `agent/service-review`：本辖区待审服务队列 + 作品预览（渲染） + 红线清单面板 + 审核动作 + 历史/审计。
- 两者归入新建的**「内容审核」分组**（用户特别强调，独立成组更醒目）。

### 11.6 后端新增/改造清单（v2 关键工作量）
- `agent-console.controller.ts`：`GET /api/agent/templates/pending`、`PATCH /api/agent/templates/:id/review`（AGENT 审核，写 reviewer/红线/意见）；服务侧 `Project` 审核端点（新增待审态 + 审核）。
- `Template` 模型：增加 `reviewStage` 或 reviewer 角色字段，区分 agent/ admin 审核记录。
- `Project` 模型：新增内容审核态（如 `reviewStatus`），发布流程改为"提交→待审→通过后公开"。
- `ContentSafetyService`：词库 DB 化（总台维护红线词库）、图片机审接入、结构化回传。
- 红线词库管理页（总台）：新增或复用 `admin/settings`，供总台配置/更新红线词库。

### 11.7 验收口径（Playwright / 接口）
- SP 提交模板 → `status=PENDING` 且**公开库 `GET /api/templates` 不返回该模板**（对外不可见）。
- 代理商 `GET /api/agent/templates/pending` 见该模板；`PATCH .../review` 通过 → 公开库出现；驳回 → 回退且带红线意见。
- 服务（`Project`）同理：提交后不公开，`reviewStatus=PENDING`；代理商通过后才可用户检索/购买。
- 角标 `templateReview`/`serviceReview` 仅统计本辖区 PENDING，数字正确。
