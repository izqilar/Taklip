# 运营端（服务商）批量请柬生成管线 — 设计说明

> 适用范围：庆柬云 / TAKLIP Cloud · 运营端 `apps/admin`(:5174) 批量请柬模块
> 复用对象：web 端（USER，:5173）已定型落地的批量请柬生成管线及其服务端内核
> 配套实现：`apps/admin/src/pages/spInvitationBatch.tsx`（批量生成工作区）、`spInvitations.tsx`（任务监控 + 名单）、`utility.ts`（`downloadWithAuth` 鉴权下载）

---

## 1. 目标

web 端的批量请柬管线已完整落地（模板选择 → 人员勾选 → 批量渲染 → 逐人进度 → 打包分发）。
运营端此前仅有「名单管理」与极简「生成任务列表」（无模板/人员选择、无逐人结果、无打包/删除/重生成），
且 Zip 下载用了相对 `/api` 路径（admin Vite 不代理 `/api`，会打到 SPA 回退页 → 404）。

本设计在**不复用任何新服务端代码**的前提下，于运营端补齐与 web 端对等的完整生成链路，并明确两端差异与运行环境约束。

---

## 2. 两端差异与运行环境约束（★ 设计锁点）

| 维度 | web 端（USER） | 运营端（SERVICE_PROVIDER） | 本端处理 |
|---|---|---|---|
| 鉴权 | `request()` 含 **401→refresh token→重试** | `authHeaders()` 裸 `Bearer`，**无 refresh** | 统一 `ApiError(401)` → `clearSession()` + 提示重登；不静默失败 |
| API 基址 | `BASE_URL=''`（走 vite proxy 仅代理 `/api`、`/uploads`、`/public`） | `API_URL='http://localhost:3000/api'`（**绝对**，Vite 不代理 `/api`） | 所有请求一律 `${API_URL}${path}`；下载一律 `downloadWithAuth`（fetch+Blob+auth） |
| UI 框架 | 自写 React + tailwind + react-i18next | antd + Refine + `T` 设计令牌 | 弹窗/表格/进度用 antd；设计令牌复用 `T` |
| 模板预览 | `InvitationTemplatePicker`（`@h5design/render` SchemaRenderer） | 复用 admin 既有 `WorkPreviewModal`（同一 SchemaRenderer） | 保证与 web 端所见即所得 |
| 作用域 | `SELF`（终端用户自身） | `ORG`（自营样板）/ `CLIENT`（代客，带 `clientId`） | `ownerType`/`clientId` 透传所有调用 |
| 角色边界 | `USER` | 以 **SERVICE_PROVIDER** 登录 | server `invitation.*` 端点已 `@Roles('USER','SERVICE_PROVIDER')` → **server 无需改动** |

### 关键约束（务必遵守）
1. **admin Vite 不代理 `/api`**：任何 `/api/...` 相对路径都会打到 SPA 回退页。所有 fetch 必须走绝对 `API_URL`；所有文件下载必须用 `downloadWithAuth`（`<a href>` 无法携带 `Authorization`）。
2. **私有资产不公开暴露**：逐人图与 Zip 均落 `private-assets`，必须经 `authHeaders()` 取。故预览图不能直链 `<img src>`，须 `AuthImage`（带鉴权 fetch → ObjectURL）。
3. **scope 入参位置不一致（server 历史约定）**：`POST /invitations/projects|selection|batch-generate` 与 `DELETE /results` 的 `ownerType`/`clientId` 在 **body**；`GET /results|jobs|download|files` 在 **query**。本端两处都带，规避分叉。
4. **无 token 刷新**：长任务轮询期间令牌过期会 401，已统一跳转重登提示。

## 4. 完整流程（四步）

### ① 选模板
- `GET /api/projects`（SP 登录列出自身作品，过滤 `pages.length>0`）→ 卡片选择。
- 选中后「预览」拉 `GET /api/projects/:id` 取 schema，经 `WorkPreviewModal`（同 `@h5design/render`）多页预览。
- 确认即 `template = {id,title}`；改模板会作废已有 `projectId`（下次保存选择以新模板重建），避免锁定快照指向旧模板。

### ② 选人员
- `GET /api/guest-lists?{scope}` 取名单 → 下拉选名单 → `GET /api/guest-lists/:listId/records?page=1&size=500` 取人员。
- 姓名搜索 + 全选/清空 + `Checkbox.Group` 勾选。
- 确认：若尚无项目则 `POST /api/invitations/projects {templateId,listId,ownerType,clientId}` 建项目；再 `POST /api/invitations/projects/:id/selection {listId,selectedRecordIds,...}` 落勾选。
- **锁定**：首次生成后 `generated=true`，模板/人员选择器禁用（服务端快照已锁定，重选不影响输出）。

### ③ 批量生成
- `POST /api/invitations/batch-generate {projectId}`（**不传 mode** → 服务端按 `DRAFT`→`FREE_SAMPLE` / 否则 `PAID` 自动判定）。
- 返回 `{jobId,total}`；置 `running=true` 进入轮询。
- 配额不足（402 `QUOTA_EXCEEDED` / `LOCKED_NEED_PURCHASE）`：明确提示「需购买人次」（购买由订单回调写入 `purchasedHeadcount`，不在本管线内）。

### ④ 进度 / 异常 / 分发
- **轮询**：每 2s 并行 `GET /api/invitations/jobs/:jobId`（终态信号）+ `GET /api/invitations/projects/:id/results`（逐人）。
  - 终态 `SUCCESS/PARTIAL/FAILED` → 停止轮询。
  - ⚠️ 不能仅凭逐人 `status` 停止：免费赠样仅渲前 3 人，其余恒为 `pending`，故必须以 **job 状态** 为完成信号。
- **逐人状态**：`ok`（成功）/ `failed`（失败，附 `error` 悬浮）/ `pending`（未渲，多为配额未购）。
- **分发操作**：
  - 打包下载全部 / 选中：`downloadWithAuth(GET /projects/:id/download?{scope}[&recordIds=])`
  - 逐人下载：`downloadWithAuth(row.url?{scope})`（`row.url` 为 `/api/invitations/jobs/:jobId/files/:recordId`）
  - 删除选中：`DELETE /projects/:id/results {recordIds}`（**不退配额**）
  - 重生成选中：`POST /batch-generate {mode:'RERENDER', targetRecordIds}`（**不耗配额**，用于模板改版/单条失败重做）

## 5. 任务调度与异常处理机制

| 场景 | 机制 |
|---|---|
| 并发 | 服务端 `RENDER_CONCURRENCY=4` 限并发 puppeteer；前端无并发负担，仅轮询 |
| 单条失败 | 逐人 `try/catch` 隔离，整 job 不中断；终态 `PARTIAL`（部分）/ `FAILED`（全失败） |
| 超时 | 服务端 `RENDER_PER_ITEM_TIMEOUT_MS=90_000` 闸门，渲染卡死也失败并释放配额 |
| 配额回退 | 失败条在收尾回退对应桶（赠样/付费），`RERENDER` 本不占配额 |
| 全有或全无 | 事务内咨询锁 + 配额扣减 + 快照锁定；首渲整体失败 `rollbackJob` 撤销快照回 `DRAFT` |
| 前端 401 | `ApiError(401)` → `clearSession()` + 提示重登（admin 无 refresh 管线，已知约束） |
| 前端 402 | 提示「需购买人次：<服务端消息>」 |
| 网络抖动 | 轮询 `catch` 容错，下次 tick 继续；仅 401 停轮询 |
| 预览图 401 | `AuthImage` 带鉴权 fetch，避免 `<img>` 直链暴露 401 |

## 6. 渲染一致性保证

- **同一渲染内核**：两端共用 `apps/server` 的 `personalizeSchema`（core 纯函数）+ `ExportService.prepareSchema` + puppeteer 截图，模板/数据/水印/分辨率口径完全一致。
- **同一预览内核**：运营端模板预览复用 web 端同款 `@h5design/render` `SchemaRenderer`（经 `WorkPreviewModal`），编辑器/预览/发布三者所见即所得。
- **不可变快照**：首渲即锁定整勾选子集（`renderSnapshot`），后续续渲/重渲都基于同一份数据，live 名单改动零影响（FR-3）。
- **逐人隔离 + 顺序输出**：并发渲染后按名单顺序重排，出图顺序 == 名单顺序。

## 8. 已知约束与后续

1. **admin 无 token 刷新**：长任务中令牌过期需重登（已在 UI 提示）。如需无缝，可后续复用 web 的 `authFetch` refresh 策略。
2. **代客(CLIENT)下载**：`sp/invitations/jobs` 监控页为轻量跨项目视图，下载按 ORG 默认作用域；CLIENT 维度的逐人/打包下载请在「批量生成」工作区内操作（已正确带 `clientId`）。
3. **购买人次**：本管线聚焦生成与分发；人次购买由订单支付回调写入 `purchasedHeadcount`，不在本页内。
4. **server 零改动**：所有配额/快照/隔离/超时逻辑沿用 web 端已验证实现，两端行为天然一致。
