## 1. 背景与目标

当前 web 与 admin 两端、以及 admin 内部不同页面，对"作品/模板卡片的鼠标停靠（hover）操作按钮"存在 **三套相互漂移的实现**，按钮语义、层级、权限门控各不相同，维护成本高且易产生体验不一致。

**目标**：将 hover 操作层抽象为统一的 **`DesignGalleryCard` 外壳组件**，跨端复用同一套交互规范与权限门控逻辑；各端仅通过 `capabilities` + `on*` 回调注入自身业务实现，实现"布局/门控 DRY、业务实现本地化"。

**本期明确的范围边界**：
- 保留并**挪位**"提交为模板"（已有能力，仅调整位置）；
- **砍掉**"降为作品"（反向降级，成本/风险与价值不匹配，详见第 7 章）。

## 3. 设计原则

1. **权限外置，组件零权限逻辑**：外壳组件只负责"按 `capabilities` 决定按钮显隐与布局"，**绝不**在组件内部判断角色/只读。权限由调用方（web 按角色/exportOnly；admin 按 `useLayer().readonly` + 对象作用域）算好后传入。
2. **共享"外壳"、本地化"实现"**&#8203;：统一的只是"封面 + 状态徽标 + 三层操作栏 + scrim + 按钮门控"这一**易漂移的展示层**；预览弹窗、详情抽屉、导出弹窗、编辑跳转、删除/提交等**业务动作留在各端**，通过 `on*` 回调触发。
3. **i18n 解耦**：外壳不绑定任何 i18n 源（web 用 react-i18next，admin 用模块级 call-time `t()`）。所有按钮文案由 host 通过 `labels` 对象（已各自 `t()` 解析）传入，外壳只渲染字符串。
4. **触屏兜底**：hover 在触屏不可用，外壳需支持"点击切换浮层 / 常驻精简操作"，不能仅依赖 `:hover`。

## 4. 统一交互规范

### 4.1 布局定稿（三层）

| 层                                            | 按钮              | 行为                                                         | 所需 capability    |
| --------------------------------------------- | ----------------- | ------------------------------------------------------------ | ------------------ |
| **顶栏**（次要/危险，居中、避开左上状态徽标） | 详情              | 打开**元数据抽屉**：标题 / 作者 / 统计 / 审计记录            | `detail`           |
| 顶栏                                          | 导出              | 打开导出弹窗（图片 JPEG/PNG/WebP、视频 MP4/WebM、GIF）       | `export`           |
| 顶栏                                          | 删除              | `Modal.confirm` 二次确认后删除（危险操作）                   | `delete`           |
| **中心**（主操作）                            | 预览              | 打开**多页渲染 + 动画重播**预览弹窗（非单图，真实还原发布效果） | `preview`          |
| 中心                                          | 编辑              | 跳转作品/模板编辑器                                          | `edit`             |
| **底部**（按 `kind` 条件出现）                | 作品→`提交为模板` | 克隆为 PENDING 模板，进入审核闸门                            | `submitAsTemplate` |
| 底部（模板）                                  | —                 | **已砍掉"降为作品"**&#8203;；模板退出服务由既有"下架"承载    | —                  |

> 说明： **“预览"≠"详情”** &#8203;。预览=多页+动效查看器；详情=元数据抽屉（属性展示，类 `SPWorkDetail`）。二者语义独立，无重叠。

### 4.2 视觉

- 封面区保持 375:667 首屏比例（`SchemaThumbnail` 真实渲染或封面图，无 schema 回退渐变占位）。
- 状态徽标固定在左上；三层操作覆盖一层**半透明 scrim** 保证按钮在任意封面上可读。
- 各端沿用自身设计令牌（web=Tailwind / admin=内联+T 令牌），外壳仅提供中性布局骨架。

## 5. 组件契约（DesignGalleryCard）

建议落地于新建 `@h5design/ui` 包（与现有 `@h5design/render` 同构），使用 **CSS Modules 中性样式**（不引入 Tailwind/内联），颜色令牌由 host 通过 style/class 注入。

```typescript
type DesignKind = 'work' | 'template';

interface DesignActionCaps {
  preview?: boolean;
  detail?: boolean;
  edit?: boolean;
  export?: boolean;
  delete?: boolean;
  submitAsTemplate?: boolean;
  publish?: boolean;        // 作品额外：发布（见第 9 章待决）
}

interface DesignGalleryCardProps {
  kind: DesignKind;
  cover?: string;
  schema?: any;             // 用于 SchemaThumbnail 真实渲染首屏
  status: string;           // draft | published | PENDING | ...
  badgeLabel: string;       // 状态徽标文案（已本地化）
  capabilities: DesignActionCaps;
  labels: Record<string, string>;   // 由 host 用各自 t() 解析后传入，外壳零 i18n 耦合
  item: any;                // 当前设计稿数据（id/title 等）
  on: {
    preview: (item: any) => void;
    detail:  (item: any) => void;
    edit:    (item: any) => void;
    export:  (item: any) => void;
    delete:  (item: any) => void;
    submitAsTemplate: (item: any) => void;
    publish?: (item: any) => void;
  };
}
```



```
const { readonly } = useLayer();           // 超级管理员=可写，运维管理员=只读
const caps: DesignActionCaps = {
  preview: true,
  detail: true,
  export: true,
  edit: !readonly,
  delete: !readonly,
  submitAsTemplate: !readonly,
};

```

## 7. 范围决策

### 7.1 提交为模板 —— 保留，仅挪位

- 能力已存在且经审核闸门验证，迁移成本极低（摆位调整）。
- 语义确认为**克隆保留**：原作品不动，另生成一份 PENDING 模板进入运营端审核队列（即"进入服务管理（审核中）"）。如未来要求"移动/原作消失"，需单独后端变更，不在本期。

### 7.2 降为作品 —— 砍掉（本期不做）

**理由**：

1. **成本非对称**：后端零实现，需新增 `demote` 生命周期（模板 `TAKEN_DOWN` + 用 `effectiveSchema` 反向生成 Project），并连带归属/草稿线上态/线上 H5 失效等坑；而"提交为模板"是白送能力。
2. **破坏性高危**：模板下架 = 线上 `/p/xxx` 链接直接断，影响真实用户，不应暴露为每张卡片 hover 的高频触点。
3. **频率/价值存疑**：模板退回成作品的场景极少；模板退出服务已有既有"下架"语义可满足；作者如需继续编辑，可从下架模板另存/克隆新作品。
4. **行业惯例**：模板市场普遍只做"单向晋升 + 下架"，不做可逆降级。

> 若产品后续确有强需求，建议改为**放进模板详情页的受控管理员操作**（带 `Modal.confirm` 强提醒、限定 ADMIN/服务商本人），而非 hover 对称按钮——本期不实现。

### 11.2 行为变更 / 与文档偏差（需产品确认）
1. **「详情」语义纠正（userPages）**：原 `UserWorkCard` 的「详情」按钮实为打开**预览弹窗**（语义错配）。现严格按规范拆分——「预览」→ 多页渲染+动画重播弹窗；「详情」→ `WorkDetailPanel` 抽屉（元数据 + 审计）。父组件 `UserWorks` 新增 `Drawer` 承载。
2. **只读态放宽**：文档 §10 验收为「只读态仅显 预览/导出/详情」，与原 `UserWorkCard`「只读仅预览」不同。已按文档执行（只读 = 详情/导出/预览；可写 = 全开）。
3. **保留 admin 监督视角「取消发布」**：文档 §4.1 顶栏未列 `unpublish`，但运营端监督已发布作品需下架线上 H5（对齐 memory §7「历史遗留已发布作品保留下架」）。外壳新增 `unpublish` capability（顶栏「导出」之后、「删除」之前），`UserWorkCard` 在 `!readonly && published` 时开启。属文档外的合理扩展。
4. **web 端「下架」入口**：web `WorkCard` hover 不再渲染历史「下架」（`onUnpublish`）—— 统一规范顶栏不含该动作；历史已发布作品的下架入口保留于作品管理/详情页。此为本次重构的已知行为变更，待产品确认是否需在 web hover 层补回。

### 11.3 顺带修复的遗留问题（providerPages，原 typecheck 从未跑过故未被发现）
- 重复 `import { useLayer }` 导致 `TS2300 Duplicate identifier`。
- 状态徽标 `badgeLabel={st.text}`：`WORK_STATUS`/`TEMPLATE_STATUS` 形态为 `{ key, tone }`（`text` 仅存在于兜底分支），正常状态 `st.text` 为 `undefined` → 徽标**整片空白**。已改为 `st.text ?? t(st.key)`，徽标恢复正常本地化文案。

### 11.4 `DesignActionCaps` 最终契约（相对 §5 增量）
在 §5 基础上新增 `unpublish?: boolean`（顶栏「导出」之后）；`use`（`template` 底部）/ `publish` 已于前期补入。
