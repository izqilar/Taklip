## 1. 背景与问题陈述

用户反馈：在编辑器（`apps/web`）中创建好的请柬，在网页端 `http://localhost:5173/dashboard` 能正常显示，但在管理后端 `http://localhost:5174/user/works` 没有正确渲染出来，两端首页渲染效果"完全不一样"。

经排查，根因**不是数据缺失，而是渲染器未统一**：

- **`5173/dashboard`** 调用 `SchemaThumbnail` → `DOMRenderer`，消费**完整 `schema`**，把每页每个元素（文字 / 图片 / 组件 widget）真实渲染为 DOM + CSS，再按缩放比缩小显示。这是"真渲染"。
- **`5174/user/works`** 此前没有接入任何 schema 渲染器，临时方案是后端 `buildSchemaPreview` 只抽取"背景色 + 1 段文字 + 1 张图"生成摘要，前端 `SchemaPreview` 仅做近似占位。因此编辑器作品（默认 `cover: null`）在后台只剩纯色 + 首字，与 5173 的真实设计天差地别。

更深层的结构性问题：`apps/admin` 甚至**未依赖 `@h5design/core`**，而 `DOMRenderer` 深度耦合 `apps/web` 的 `@/` 路径别名与内部组件，无法直接被后台复用。

未来需求：在 **Web 端、H5 客户端、微信小程序** 三个终端都达到统一的作品展示效果。本方案据此给出"单一 JSON 模板 + 单一渲染器真源"的系统化改造路径，小程序首期采用 **A 方案（web-view 嵌入发布页）**。

## 2. 现状分析（As-Is）

### 2.1 数据模型与 JSON 模板现状（已具备）

`packages/core/src/schema.ts` 定义了全平台统一的 `Project → Page[] → Element[]` 模型（23 种元素类型 + `widget` 复合类型），文件头明确声明其为"单一数据源"，被编辑态（Konva）与发布态（DOM）渲染器共同消费。**这是天然的统一 JSON 模板，已存在，无需重写。**

`packages/core/src/index.ts` 当前仅：

```ts
export * from './schema';
export * from './constants';
```

即 core 目前只承载**类型与常量**，不含任何 React 渲染代码。


### 2.2 渲染管线现状（双轨、不一致）

| 端            | 文件                                                                             | 渲染方式                                      | 数据源                                       | 结果   |
| ------------ | ------------------------------------------------------------------------------ | ----------------------------------------- | ----------------------------------------- | ---- |
| Web `5173`   | `apps/web/src/components/Preview/DOMRenderer.tsx`（默认导出）+ `SchemaThumbnail.tsx` | 完整 schema → DOM/CSS，缩略图 `animated=false`  | `GET /api/projects` / `:id` 返回完整 `schema` | 真实设计 |
| Admin `5174` | `apps/admin/src/pages/userPages.tsx` 内 `SchemaPreview`（行 1270–1328）            | 仅读后端 `schemaPreview` 摘要（bg+text+image）做占位 | `GET /api/user/works` 返回 `schemaPreview`  | 近似占位 |
| 编辑器画布        | `apps/web/.../KonvaElement.tsx` 等                                              | Konva 画布渲染                                | 同一 `schema`                               | 编辑态  |

`DOMRenderer.tsx` 关键结构（决定抽取范围）：

- 行 821：`export default function DOMRenderer({ project, scale, animated })` — 主渲染器
- 行 843：`export function PublishedH5({ project })` — 发布页整页渲染（含多页切换）
- 行 69：`ImageElementView` 等内联元素视图
- 依赖（需解耦）：`@/animations/presets`(GSAP)、`@/utils/sanitize`(safeLink/safeMedia/safeBackgroundImage)、`@/utils/externalVideo`、`@/components/UI/ColorPicker`(parseCssColor/rgbaToCss)、`@/elements/*/DOMXxx`（calendar/gallery/puzzle/countdown/mapNav/messageBoard/timeline/like/widget）

> 注：缩略图场景 `animated=false`，GSAP 入场动画不参与，因此共享渲染器可把动画播放器设为可选依赖，降低抽取成本。

### 2.3 小程序现状

尚无独立渲染实现。已具备发布页能力：`GET /api/p/:publishCode` 返回 `{ title, schema }`，前端 `PublishedPage.tsx` 在 `/p/:publishCode` 渲染完整 H5。该 URL 即可作为小程序 web-view 的数据源。

### 2.4 根因小结

1. **渲染器未共享**：5173 用真渲染器，5174 用近似占位，故"完全不一样"。
2. **依赖未打通**：admin 未依赖 core，且 `DOMRenderer` 耦合 web 内部路径，无法直接复用。
3. **渲染逻辑下沉到后端是弯路**：`buildSchemaPreview` 把"渲染"做成服务端摘要，既近似又无法覆盖全部元素，应回归"前端用统一渲染器渲染完整 schema"。

## 3. 目标架构（To-Be）


### 3.1 分层架构

```
                ┌──────────────────────────────────┐
                │  packages/core/src/schema.ts      │
                │  Project → Page[] → Element[]     │  ← 唯一 JSON 模板（单一数据源）
                └──────────────────┬───────────────┘
                                   │
                ┌──────────────────▼───────────────┐
                │  @h5design/render（新建共享包）     │
                │  SchemaRenderer / SchemaThumbnail  │  ← 唯一渲染器真源（纯 React）
                └──────────────────┬───────────────┘
            ┌──────────────────────┼───────────────────────┐
            ▼                      ▼                       ▼
      apps/web (5173)        apps/admin (5174)       微信小程序（A 方案）
      SchemaThumbnail        UserWorks 卡片          <web-view src=/p/:publishCode>
      = 像素一致             = 像素一致               = 复用 5173 发布产物
```

设计原则：

- **单一模板**：`schema.ts` 是唯一作品描述，任何端不另立字段。
- **单一渲染器**：所有"展示作品"的场景都调用 `@h5design/render`，杜绝分端近似实现。
- **生产/消费同源**：编辑器（Konva）只负责产出 `schema`；展示端只负责消费 `schema`，二者通过同一份类型契约对齐。
- **小程序零重复**：通过 web-view 直接加载已发布的 H5 页（即 5173 的渲染产物），天然三端一致。

## 4. 改造方案详述

### 阶段一：Schema 层加固（低风险，先落地）

目标：为"设计一次、长期兼容"提供契约保障。

- 在 `Project` 类型中增加可选 `version: number`（默认 `1`），标识 schema 语义版本。
- 在 `@h5design/render`（或 core）提供 `normalizeSchema(project)` 迁移函数：对缺失新字段的老作品做兜底补全，保证旧 JSON 也能被新渲染器消费。
- 在 `project.service` 落库 / 读取时调用 `normalizeSchema`，做到读写透明。

验收：老数据（seed / 历史作品）无报错渲染；新作品带 `version` 字段。


### 阶段二：新建共享渲染器包 `@h5design/render`

这是本次改造的核心。把 `apps/web` 的 `DOMRenderer` 及其依赖抽离为独立 workspace 包。

**包结构**

```
packages/render/
  package.json        # name: @h5design/render; peerDeps: react, react-dom; devDeps: typescript
  tsconfig.json       # jsx: react-jsx, 引用 core
  src/
    index.ts          # export { SchemaRenderer, SchemaThumbnail, PublishedH5, normalizeSchema }
    SchemaRenderer.tsx      # 由 DOMRenderer 改造：去除 @/ 依赖
    SchemaThumbnail.tsx     # 由 apps/web 的 SchemaThumbnail 上移（含 ResizeObserver + IntersectionObserver 懒渲染）
    PublishedH5.tsx         # 由 DOMRenderer.PublishedH5 上移
    elements/               # 各 DOM* 元素组件由 apps/web/src/elements/*/DOMXxx 上移
    lib/                    # sanitize / color / externalVideo 等纯函数由 apps/web 上移
```

**解耦要点**

- 所有 `@/...` 导入改为包内相对导入；`playElementAnimation`(GSAP) 改为可选：渲染器接收 `animated` 参数，缩略图传 `false` 时跳过动画播放器（与 5173 现状一致），从而**不强制**共享包依赖 GSAP。
- `sanitize`（safeLink/safeMedia/safeBackgroundImage）、`ColorPicker` 的颜色函数（parseCssColor/rgbaToCss）、`externalVideo` 解析器一并迁入 `lib/`，保持纯函数、无副作用。
- 渲染产物为**无样式框架依赖的纯 `<div>` + 内联 style**，可安全嵌入 antd Card（admin）或裸容器（web）。

**依赖调整**

- `packages/render/package.json`：`peerDependencies: { react, react-dom }`，`dependencies: { @h5design/core: workspace:* }`。
- `apps/web/package.json` 与 `apps/admin/package.json` 均增加 `"@h5design/render": "workspace:*"`。
- `pnpm-workspace.yaml` 已含 `packages/*`，无需额外改。

### 阶段三：Admin 接入共享渲染器（修复 5174 渲染）

在 `apps/admin/src/pages/userPages.tsx`：

1. 删除本地 `SchemaPreview` 函数（行 1270–1328）及其引用（行 1425–1431）。
2. 引入共享渲染器：`import { SchemaThumbnail } from '@h5design/render';`
3. 卡片封面区改为：进入视口后按需拉取**完整 schema** 并渲染：
   - 列表 `GET /api/user/works` 仅返回轻量字段（见阶段四）；
   - 卡片挂载时（可复用 `SchemaThumbnail` 自带的 `IntersectionObserver`）调用 `GET /api/projects/:id` 取完整 `schema`，交给 `SchemaThumbnail` 渲染——**与 5173 像素一致**。
4. 移除 `utility.ts` 中仅为近似预览新增的 `STATIC_URL`（若不再被其他逻辑使用）。

> 说明：admin 当前是 React18 + antd5 + Refine。共享渲染器输出纯 div，不冲突；状态标签"草稿/已发布"等仍由 admin 自身用 `T.*` 主题色渲染，保持后台视觉规范。

### 阶段四：后端接口收敛

`apps/server/src/console/user-console.controller.ts`：

- **删除** `buildSchemaPreview`（行 131–146）及其在 `works` 中的调用（行 405）。
- `GET /api/user/works` 返回字段收敛为：`id, title, cover, status, publishCode, viewCount, createdAt, updatedAt`（去掉 `schema/schemaPreview`）。`cover` 为空时前端自行按需取完整 `schema` 渲染，无需后端摘要。
- 保留并复用已有 `GET /api/projects/:id`（行 35）返回完整 `schema` 作为卡片渲染数据源。
- 若担心列表卡片逐个请求 `:id` 的并发，可改为 `works` 接口支持 `?withSchema=1` 一次性返回（但默认不返回，控制体积）。

验收：前后端均不再出现 `schemaPreview` 字段；5174 作品卡片与 5173 同源渲染。

### 阶段五：小程序 A 方案（web-view 嵌入）

- 小程序侧新增页面 `pages/work-preview`，用 `<web-view src="{{h5Url}}">` 加载。
- `h5Url` 由作品 `publishCode` 拼出：`https://<业务域名>/p/<publishCode>`（复用 `GET /api/p/:publishCode` 已发布的 H5 页）。
- 未发布作品（草稿）在小程序内提示"请先发布后再查看"，或跳转 web 端编辑页。
- **前置条件**：在微信公众平台配置业务域名白名单（含后端域名），否则 web-view 无法加载。
- 数据贯通：发布页本身即 `@h5design/render` 的产物（与 5173 同源），因此小程序展示与 Web / Admin **天然一致**，无需任何额外渲染代码。

> 远期可选 B 方案（原生渲染器）：若后续要求小程序内原生卡片列表而非整页 web-view，再基于同一 `Project` JSON 编写"schema → WXML/WXSS"翻译器。本阶段不做。

## 6. 渲染 / 数据流程

**列表 + 卡片渲染（web / admin 一致）**
```
用户进入"我的作品"
  → GET /api/user/works  (轻量列表: id/title/cover/status/publishCode/viewCount)
  → 渲染卡片网格（封面区）
       ├─ cover 存在 → 直接 <img>
       └─ cover 为空 → SchemaThumbnail 进入视口
            → GET /api/projects/:id  (完整 schema)
            → @h5design/render 渲染 → 与 5173 像素一致
```

**小程序（A 方案）**
```
小程序打开作品预览
  → 取 publishCode
  → <web-view src="https://域名/p/{publishCode}">
  → 加载 5173 已发布 H5（= @h5design/render.PublishedH5 产物）
```

## 7. 兼容性与迁移

- **旧作品 JSON**：通过 `normalizeSchema` 在读写时补全新字段，老数据无需批量迁移即可渲染。
- **admin 视觉规范**：状态标签、间距、主题色仍由 admin 用 `T.*` 控制，渲染器只负责"画布内容"，不破坏后台 UI 规范。
- **包构建顺序**：`startup` 脚本需在 `web`/`admin` 之前先 `pnpm --filter @h5design/render build`（参照现有 `@h5design/core` 的构建顺序）。
- **回滚**：各阶段相互独立，阶段二/三可单独回滚（保留 `SchemaPreview` 旧代码直至共享渲染器验证通过后再删除）。

## 9. 风险与回滚

| 风险 | 影响 | 缓解 |
|---|---|---|
| 抽取 `DOMRenderer` 时遗漏内部依赖（如某 `DOMXxx` 组件） | 渲染缺元素 | 按 `import` 清单全量迁移 + V1/V2 截图比对 |
| 共享包引入 GSAP 致 admin 包体增大 | 非关键 | 缩略图 `animated=false` 时跳过动画播放器，GSAP 不进共享包主路径 |
| `works` 改为按需取 `:id` 增加请求数 | 列表多作品时并发 | 可加 `?withSchema=1` 开关；或保持 `cover` 预生成 |
| 小程序业务域名未配置 | web-view 空白 | 上线前在公众平台加白名单；提供降级提示 |
| HMR 期间 `LayerProvider` 重挂载致监督对象丢失（历史坑） | 调试误判 | 验证用硬刷新 + 干净重启，非本次改动引入 |

## 11. 附录：关键接口契约

- `GET /api/user/works?userId=<id>` — 轻量作品列表：`{ items: [{ id, title, cover, status, publishCode, viewCount, createdAt, updatedAt }], total }`
- `GET /api/projects/:id` — 完整作品：`{ id, title, schema, status, publishCode, ... }`（schema 即 `Project` JSON）
- `GET /api/p/:publishCode` — 已发布 H5：`{ title, schema }`（小程序 web-view 数据源）
- `Project`（JSON 模板）— 定义于 `packages/core/src/schema.ts`，全端唯一。
