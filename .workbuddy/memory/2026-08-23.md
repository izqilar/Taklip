## 发布管线导出第五轮修复（根因：safeMedia 误杀所有 data: 图片）—— 已闭环
- 用户反馈：视频导出已正常；但图片导出（当前页/长图）图片对象仍是 "Image" 占位、且背景图/背景色透明度未正确渲染。
- **根因（确定性 bug，前四轮都没抓到）**：`apps/web/src/utils/sanitize.ts` 的 `safeMedia` 白名单正则为 `^(https?:|data:image\/)`，并用 `new URL(trimmed).protocol` 判断。但 `new URL('data:image/png;base64,...').protocol` 返回的是 `'data:'` 而非 `'data:image/'`，导致正则匹配失败、`safeMedia` 把**所有 `data:` 图片一律返回空串**。
- 影响链：`exportVideo.cloneAndInline` 把图片预加载成 dataURL 写回 `el.src` → `DOMRenderer.ImageElementView` 用 `safeMedia(el.src)` 过滤时被清空 → `!imgSrc` 分支渲染 "Image" 占位（这就是图片永远是占位、且视频正常的原因——视频走 Konva 渲染不经过 safeMedia）。同时 `AnimatedPage` 的 `backgroundImage: url(${safeMedia(page.backgroundImage)})` 也把内联后的背景图 dataURL 清空 → 背景图丢失。
- 修复：`safeMedia` 改为先判相对路径放行；再对 `^data:` 仅放行 `data:image/|data:video/|data:audio/`，拦截 `data:text/html` 等危险协议；其余走 `new URL().protocol` 必须是 `https?:`。删除已无人引用的 `MEDIA_PROTOCOL` 常量。
- 背景色透明度：数据库实测 `page.background` 存为 `rgba(223,185,145,0.49)` 这类带 alpha 格式；`rgbaToCss(parseCssColor(...))` 能正确保留 alpha，且 `EditorApp.tsx` 的 `toPng` 未设 `backgroundColor`（html-to-image 仅在显式传 backgroundColor 才铺底），故半透明背景会正确保留进 PNG，本身无 bug。
- 验证：前端 `tsc --noEmit` EXIT=0。本次修复同时让预览/发布页也能显示 data: 图片（原来被同一 bug 误杀）。用户刷新浏览器即可验证图片内容与背景图恢复。

## 发布管线导出第六轮修复（根因：背景图 url() 二次包裹 + safeMedia 对 url(...) 抛错）—— 已闭环
- 用户反馈：第五轮修复后图片对象已正常，但 **页面背景图完全不渲染**、且背景色透明度观感不对。
- **根因（确定性 bug）**：`exportVideo.cloneAndInline` 把 `page.backgroundImage` 处理成 `url(data:image/webp;base64,...)`（已 `url(...)` 包裹）写回 `page.backgroundImage`；而 `DOMRenderer.AnimatedPage` 里 `backgroundImage: url(${safeMedia(page.backgroundImage)})` 又对「已是 url(...) 包裹」的值整体调用 `safeMedia`——`new URL('url(data:...)')` 抛错 → `safeMedia` 返回空串 → `backgroundImage: url()` 非法 → 背景图彻底丢失。编辑器常态下 `page.backgroundImage` 是裸 `/uploads/x.webp`，`safeMedia` 直接放行，故编辑器/预览正常、唯独导出态缺背景图。
- 修复：在 `apps/web/src/utils/sanitize.ts` 新增 `safeBackgroundImage(value)`，统一处理「裸 URL」与「`url(...)` 包裹」两种形态（提取内部地址 → `safeMedia` 校验 → 重新包 `url(...)`），`data:text/html` 等危险协议仍拦截；`DOMRenderer.AnimatedPage` 改用 `safeBackgroundImage(page.backgroundImage)`。
- 背景色透明度：本就无 bug（`page.background` 的 `rgba(...,0.49)` 经 `rgbaToCss` 保留 alpha，`toPng` 未强制白底）。用户感知的"透明度不对"实为背景图缺失导致整页观感错位；背景图恢复后预期一致。（如刷新后仍显 opaque，需进一步查 html-to-image 对 foreignObject 半透明底的合成——待用户复测反馈。）
- 验证：前端 `tsc --noEmit` EXIT=0。

## 发布管线导出第七轮修复（背景色透明度「映射」丢失，还原编辑器观感）—— 已闭环
- 用户反馈：图片/视频导出都通了，但**页面背景色的半透明在导出中观感不对、像透明度丢失**。
- 根因定位：页面背景 `page.background` 存 `rgba(223,185,145,0.49)`（半透明），在**编辑器**里是叠在画布容器底色 `#f0f2f5`（EditorApp 的 `<main className="...bg-[#f0f2f5]">`）之上的半透明色调；而导出时：
  - 图片：`html-to-image.toPng` 默认**不垫底**（透明），在白色查看器下观感偏浅；
  - 视频：`konvaVideoExport` 录制画布预填**纯白** `#ffffff`，半透明背景叠在纯白上 → 偏浅且更显「不透明」。
  - 两者底色都 ≠ 编辑器 `#f0f2f5`，故半透明映射错位、看起来像透明度丢失。
  - （注：颜色解析 `parseCssColor`/`rgbaToCss` 与 `buildPageBackground` 的 rgba 透传均正确，非根因。）
- 修复（按用户选择「还原编辑器观感」）：
  - `EditorApp.tsx` 两处 `toPng` 增加 `backgroundColor: '#f0f2f5'`；
  - `konvaVideoExport.ts` 录制画布初填与 `recorder.start` 后补帧、`makeBlankCanvas` 兜底帧，底色由 `#ffffff` 改为 `#f0f2f5`。
- 验证：前端 `tsc --noEmit` EXIT=0。刷新后导出图片/视频的背景半透明色调应与编辑器一致。
- 备注：若后续需要「PNG 保留真·alpha 透明通道（可叠在其他设计稿）」，把两处 `backgroundColor` 去掉即可；视频 mp4 不支持透明，需改输出 WebM 透明视频才可行。

## 发布管线导出第八轮修复（视频录制偶发「内容为空」回归）—— 已闭环
- 用户反馈：第七轮后「刚才视频导出还正常，现在突然报录制内容为空」。
- 根因分析：第七轮仅修改导出底色 #ffffff→#f0f2f5，本身不会导致录制为空；真正高概率根因是 MediaRecorder 停止时序问题：Chromium 下 `onstop` 有时早于最后一个 `dataavailable` 触发，导致代码在 `onstop` 里立即检查 `chunks.length` 为 0 而 reject。另外 `createRecorderForExport` 音频失败 fallback 时二次调用 `canvas.captureStream(fps)` 也可能引入流状态问题。
- 修复：
  - `konvaVideoExport.ts`：
    - 移除可能引入副作用的 500ms `logTimer`（访问 `recorder.stream` 等非标准属性可能不稳定）；
    - `stopRecorder` 先 `requestData()` 强制 flush 末段数据，再 `stop()`；
    - `onstop` 中若 `chunks` 为空，等待 300ms 看是否有迟到的 `dataavailable`，避免过早 reject；
  - `audioCapture.ts`：
    - `createVideoAudioStream` 增加 `aTrack.muted` 判断，不可用的音轨直接降级为纯视频；
    - `createRecorderForExport` 只调用一次 `createVideoAudioStream`，回退纯视频时复用同一个流的视频轨（`new MediaStream(combinedStream.getVideoTracks())`），避免多次 `captureStream`。
- 验证：前端 `tsc --noEmit` EXIT=0。需用户 Ctrl+F5 强刷后复测视频导出。
