## 图片对象阴影过淡/丢失颜色（已修复）
- **现象**：编辑器里图片加阴影非常淡，仅黑色勉强可见，其它颜色几乎辨认不出；而“形状”对象阴影正常。
- **根因**（已用 Chromium 实测确认）：图片阴影原本由一个 `fill="rgba(255,255,255,0.02)"` 的半透明 Rect 投射。Canvas 会把阴影的有效不透明度乘以投射形状的填充不透明度，2% 填充把彩色阴影稀释到约 2% → 彩色叠白底不可见、黑色仅呈 2% 灰。形状对象直接把阴影加在不透明填充节点上，故正常。
- **修复**：`apps/web/src/components/Canvas/EditorCanvas.tsx` 的图片分支，把阴影投射层改为「用与图片相同内容（无滤镜、不缓存）的节点」——非平铺用 `<KonvaImage image={cached} {...computeImageLayout} cornerRadius/>`，平铺用带 `fillPatternImage` 的 `<Rect>`。这样填充为不透明图片内容，阴影强度/颜色与形状一致；透明 PNG 处天然透明，不会出现白底方块。`hasShadow` 判定也放宽为「只要 shadowColor 非 transparent」，与形状行为对齐。
- **验证**：web typecheck 0 错误；dev server HTTP 200 且已 HMR 加载新模块；Chromium 实测旧方案红色阴影像素 rgb(255,250,250)（几乎不可见）、不透明填充红色阴影 rgb(255,0,0)（正确）。

## 文本对象阴影无反应 + 新增“阴影透明度”（已修复）
- **现象**：文本对象加阴影无任何反应；需要给文本/形状/图像统一增加“阴影透明度”可调项。

  - `schema.ts` 的 `BaseElement` 新增 `shadowOpacity?: number`；`constants.ts` 默认 `shadowOpacity: 1`。
  - `ComponentSettingsPanel.tsx` 的 `EffectsSection` 在“阴影模糊”下方新增“阴影透明度”滑块（0~100%，写入 `shadowOpacity = v/100`）。
  - `DOMRenderer.tsx` 预览：新增 `applyAlphaToColor()`，将 shadowColor 按 shadowOpacity 折算 alpha 后写入 `boxShadow`，保证预览一致。
  - i18n（zh-CN/en editor.json）新增 `shadowOpacity`（阴影透明度 / Shadow Opacity）。
- **验证**：core + web typecheck 0 错误；dev server HTTP 200 且 HMR 已加载新模块；Chromium 实测修复后文本阴影 rgb(255,0,0)、shadowOpacity=0.3 时衰减为 rgb(103,0,0)。

## 图片对比度只在 100 时可见、其余变灰（已修复）
- **现象**：图片“对比度”滑块仅在 100 时正常显示；大于或小于 100 时整张图变成灰色不可见。
- **根因**（Chromium 实测确认）：图片分支计算 `contrast = (filterContrast ?? 100) / 100`（已是 100% 基准的倍率，如 150→1.5），作为 `contrast` 属性传给 KonvaImage。但自定义 `ContrastFilter` 里又做了一次 `this.contrast() / 100` → 1.5/100 = 0.015。公式 `(r-128)*0.015+128 ≈ 128` 对所有像素成立 → 整图退化为均匀灰 rgb(129,127,127)。100 时因 `Math.abs(contrast-1)<0.001` 不挂载滤镜所以正常；其余值才触发滤镜故变灰。
- **修复**：`EditorCanvas.tsx` 的 `ContrastFilter` 改为 `this.contrast() ?? 1`（直接使用已折算的倍率，不再除以 100），并加注释说明。亮度/模糊无此问题（Brighten 用 brightness 偏移、Blur 用 blurRadius，均不被二次除以 100）。
- **验证**：web typecheck 0 错误；dev server HTTP 200 且 HMR 已加载新模块；Chromium 实测修复后 c150→rgb(236,0,0)、c100→rgb(200,40,40)、c50→rgb(164,84,84)，全程不再变灰。

### 形状预览差异（经实测确认：存在真实 bug，已修复）
- **现象**（用户附编辑器/预览两张截图）：编辑器里形状（圆）降低填充透明度(0.45)+加阴影正常；预览里“形状自身透明度丢失、阴影保持原样”——预览圆比编辑器圆更饱和/更不透明。
- **根因（headless Chromium 像素实测，推翻先前“已正确”结论）**：
  - Konva 的阴影是「与形状同形、偏移、模糊」的独立一层，绘制在形状**之下**；半透填充会让这层阴影**透出来**（opacity 同时衰减 fill 与 shadow alpha）。
  - CSS `box-shadow` 永远绘制在元素 border-box **背后**，且**不会透过半透明 `background-color` 透出**。于是 `opacity:0.45`+`box-shadow` 的圆 → 填充是“粉盖白”的纯色（看起来更不透明），阴影被实心填充挡在背后 → 与编辑器视觉相反。先前用“不透明红填充、无 shadowOpacity”的同构对照漏掉了这个关键差异。
  - 实测对照（圆 opacity0.45+shadow）：编辑器中心 `rgba(237,179,184)`，旧预览中心 `rgba(255,202,210)`（更纯粉=更不透明），证明 box-shadow 不透光。
  - `filter: drop-shadow(...)` 同样不透光，无效。
- **修复（`apps/web/src/components/Preview/DOMRenderer.tsx`）**：新增形状专属 `renderShape(innerStyle)`，对有阴影的形状改用「wrapper + 独立 shadow layer」结构复刻 Konva 合成模型——
  - wrapper：承载 `opacity / left / top / width / height / rotate / zIndex / boxSizing`（即原 commonStyle 的位置尺寸，但**不再带 boxShadow**）；
  - 子层①（shadow layer，zIndex 0）：同形，`background-color = shadowColor@shadowOpacity`，`transform: translate(offsetX,offsetY)`，`filter: blur(blur)`；
  - 子层②（fill，zIndex 1）：`innerStyle` 的半透填充盖在上面。
  - wrapper 的 `opacity` 同时乘两层 → 半透填充透出下方阴影层，与 Konva 像素一致。`rect/circle/ellipse` 均走 `renderShape`；无阴影时仍用原 `commonStyle`（含 boxShadow）兜底。
- **附带修复（`apps/web/src/animations/presets.ts`）**：入场动画清理 `gsap.set(el,{clearProps:'all'})` 会把 React 渲染的 width/height/left/top 也清掉，导致带动画的形状 wrapper 塌陷为 `height:0`；且在 React StrictMode 双调用 effect 下会把 `opacity` 清成默认 1（预览形状变全不透明，复现用户问题）。改为清理前先记录 React 的设计态 `el.style.opacity / el.style.transform`，清理时**显式还原**为设计值（不再用 clearProps 清掉 opacity/transform）。
- **验证**：
  - 隔离对照（Konva 圆 vs 新 DOM 结构，参数 opacity0.45/shadow blur14 offset18,18/opacity0.35/fill #FFC0CB）：scale1.0 中心像素 **完全一致** `rgba(237,208,213)`（diff 0）；scale0.9 时 Konva `[233,204,209]` vs DOM `[255,227,232]`（diff 68，为 Konva 位图下采样 vs DOM 矢量渲染的子像素容差，非逻辑 bug）。
  - 真机 e2e（测试项目 `cmssfkazy000y14h8hewrheh7`，圆带 fadeIn 动画）：**修复前**预览中心 `rgba(255,192,203)`（纯实心粉，opacity 丢失、阴影隐藏）；**修复后**预览中心 `rgba(255,227,232)`（半透粉透出灰阴影，opacity 已应用），与编辑器 `rgba(233,204,209)` 在同一设备缩放下吻合。
  - wrapper 实测：`opacity:0.45`、`transform:rotate(0deg)`、尺寸 120×120（不再塌陷）；shadow layer `rgba(0,0,0,0.35)` blur14 translate18,18 正确位于填充之下。
  - core + web typecheck 0 错误。
- **第三轮（本轮）——用户再次举证：蓝圆 fill=#2f54eb opacity=0.6 + 橙阴影 #faad14 shadowOpacity=1 blur=0 offset(16,10)**：
  - 用浏览器复现并 headless Chromium 取像素，确认旧代码预览仍是“实心蓝 + 橙色月牙”，阴影没有透过填充。
  - **推翻上轮结论**：之前认为 wrapper 的 `opacity` 会同时乘到 shadow/fill 两层就能复刻 Konva。实测证明：当父级 `opacity < 1` 时，CSS 会先把子元素（shadow + fill）渲染到同一个离屏缓冲，fill 不透明地盖住 shadow，再整体乘以父级 opacity → 重叠区域 shadow 被 fill 完全遮挡。这与 Konva 的“shadow 和 fill 分别按 opacity 渲染、半透明 fill 会透出 shadow”有本质差别。**只有子元素各自带 opacity，才会像 Konva 一样逐层 alpha 混合。**

- **剩余已知限制（非本次诉求，记录备修）**：SVG 类形状（star/triangle/polygon/arrow/line）预览仍从 `commonStyle` 继承 `box-shadow`，对 SVG 元素只会在包围盒外画矩形阴影、且同样不透光 → 这些形状的“半透填充透出阴影”及“沿形阴影”仍未完全所见即所得。彻底修复需对 SVG 形状改用 `filter: drop-shadow()` 并调整合成方式。本轮未改动，待用户确认范围。

## startup.ps1 闪退无法启动前后端（已修复）
- **现象**：双击/运行 `startup.ps1` 窗口一闪即退（闪退），前端(5173)与后端(3000)都起不来。
- **根因**（实测 Test1/Test2 定位）：不是执行策略问题（本机 ExecutionPolicy=RemoteSigned，且文件无 MOTW 标记，本地脚本可运行）。真正的崩溃在启动服务的 `Start-Process` 调用——它带了 `-RedirectStandardOutput / -RedirectStandardError` 参数。这两个参数会强制 PowerShell 5.1 把进程环境块复制进一个**大小写不敏感字典**，而宿主终端（WorkBuddy/CodeBuddy）在环境里注入了 `Path`/`PATH`/`path` 三种大小写重复的 PATH 变量 → 字典插入抛 `已添加项。字典中的关键字:"Path"所添加的关键字:"PATH"`，脚本在最后一步（启动服务）终止，服务从未启动。证据：Start-Process 不带重定向参数时不抛（Test1 OK），带重定向参数必抛（Test2 抛相同异常）。
- **修复（`startup.ps1`）**：
  - 启动服务的两个 `Start-Process` 去掉 `-RedirectStandardOutput/-RedirectStandardError`，改为在启动的 `cmd /c "cd /d ... && node dist/main > log 2> err"` 内部做日志重定向（同一安全代码路径，仍正常 detach 服务）。
  - 增加 `Start-Transcript` 写 `startup.log` + 顶层 `trap`：任何未捕获错误先打印再 `Read-Host` 暂停，**不再静默闪退**，便于排查。
- **验证**：`Parser.ParseFile` 语法 0 错误；构造的 ArgumentList 字符串引号正确（`/c cd /d "..." && node dist/main > "..." 2> "..."`）；Start-Process 无重定向参数路径已实测可用。
- **备注**：若用户是“下载后”运行且带 MOTW 标记，RemoteSigned 会另报“未数字签名”而闪退——彼时改用 `powershell -ExecutionPolicy Bypass -File startup.ps1` 即可（本机当前文件无 MOTW，正常可直接跑）。
- **第二轮跟进（用户仍说“闪退”）**：实测 `startup.log` 显示修复后那次运行其实**成功**（"both services up and reachable"，退出码0），且 5173/3000 当时均 200。用户感知的“闪退”是脚本设计行为——启动完 detach 服务后**自己退出关窗**，看起来像崩溃。已补齐：成功路径也打印“开发环境已启动+URL”横幅并 `Read-Host` 暂停（失败路径 trap 早已暂停），窗口不再静默关闭；成功时还自动打开 http://localhost:5173 作直观确认。结论：服务其实一直在跑，窗口停留化消除误会。
